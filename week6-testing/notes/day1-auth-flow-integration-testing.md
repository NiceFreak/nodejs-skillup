## 1. W5 最终收口

### 1.1 Worker 最小对比

#### 本人预测

`/blocking` 中的 `fib(40)` 由 JavaScript 主线程同步执行。计算期间主线程无法处理定时器和新的 HTTP 回调，因此：

- 并发 `/ping` 会等待主线程恢复，延迟明显升高。
- heartbeat callback 不能按约定间隔执行，`maxHeartbeatGap` 会接近主线程的计算占用时间。

Worker 版把同一计算交给独立 Worker 线程，主线程可以继续处理 `/ping` 与 timer。它改善的是服务响应性，不保证单次计算更快。

#### 2026-07-27 实测

| 场景 | `fib(40)` 耗时 | 并发 `/ping` | `maxHeartbeatGap` |
|---|---:|---:|---:|
| 空闲基线 | - | 约 2–3 ms | 约 102 ms |
| `/blocking` | 1111 ms | 峰值约 378 ms | 1154 ms |
| `/worker` | 1124 ms | 约 2–3 ms | 102 ms |

证据支持：

- 主线程版会拖延 heartbeat 和并发请求。
- Worker 版保持主线程响应，但 `fib(40)` 本身没有加速，且还可能包含线程创建与通信开销。
- 适合 Worker 的是足够重的 CPU 密集任务，例如图像处理；简单参数校验或本来就能异步等待的 I/O 不应默认交给 Worker。

证据边界：

- `/ping` 在 CPU 任务已经执行一段时间后才发出，因此它的 378 ms 不是完整计算耗时。
- 这是一轮受控本机实验，不能直接外推生产吞吐或最优 Worker 数量。

### 1.2 到期债务重建结论

| 编号 | 知识点 | 本日掌握证据 |
|---|---|---|
| ① | 自然月边界 | 能把需求改为“本月及前两个月”，推导三个月自然月范围、`[start, end)` 半开区间及跨年 / 月末测试 |
| ② | 注册竖切 | 能按真实代码复述 `Repository(11000 → EmailConflictError) → Service / Controller 透传 → Express 5 → 全局 error handler(409)` |

| ④ | 最小 RBAC | 能基于 `validateToken → requireRole → controller` 真实链路说明角色来源、现有中间件扩展点和 401 / 403 分界 |

### 1.3 W5 四问的当前结论

- 最改变业务判断的模型：Stream。面对大文件和转发链路时，会先判断能否分块处理、是否遵守背压，而不是默认整块读入内存。
- 仍需继续消化的概念：threadpool、I/O 执行归属与慢点诊断。当前能划分证据边界，但真实系统中的竞争来源仍需结合观测判断。
- 最能证明不只会背名词的 demo：事件循环 / 主线程阻塞对照。能够从执行归属预测 timer 和 HTTP 延迟，再用实验验证。
- 对 W6 的作用：事件循环帮助解释测试挂起和并发延迟；`pipeline()` 帮助理解 CI / 数据链路的统一失败出口；错误边界与 graceful shutdown 帮助判断集成测试资源是否真正收口。

### 2.2 真正的风险缺口

现有 `monthly-sales.test.js` 中的 token 由测试代码直接签发。这能验证报表、`validateToken` 和 `requireRole` 的一部分行为，但没有保护下面这条真实衔接：

```text
登录 Service 签发 token
→ Controller 按当前响应结构返回 token
→ 客户端使用该 token
→ validateToken 验签并写入 req.auth.sub
→ requireRole 根据 sub 查询数据库中的最新角色
→ 受保护资源放行或拒绝
```

若登录签发字段、secret、payload 结构或后续验证契约发生错位，原有“直接签发 token”的报表测试可能仍然通过。

### 2.3 一次越界选择及纠正

第一轮把“登录失败次数限流”选为最高优先级，但当前项目并没有限流、Redis、验证码或邮件激活。这个方向属于有价值的安全 backlog，不属于“保护当前已有行为”的测试补全。

本日保留的原则：

```text
先为已存在、用户正在依赖的契约补回归保护
→ 再讨论尚未实现的新安全需求
```

最终优先级改为：保护“真实登录签发的 token 能被受保护资源接纳”。

## 3. 第一条认证链：真实 admin token → 报表 200

### 3.1 测试契约

输入：数据库中已有一个符合当前密码规则的 admin 用户，使用真实邮箱和明文密码调用 `POST /auth/login`。

输出：

1. 登录返回 `200`。
2. `body.payload.accessToken` 存在且为非空字符串。
3. 使用该 token 请求 `GET /reports/monthly-sales` 返回 `200`。

第三项才是 token 能被当前认证 / 授权链接纳的核心证据。第二项只证明输出形状，不能单独证明它是有效 JWT。

### 3.2 fixture 选择

admin fixture 直接通过 `User.create()` 写入测试数据库，密码哈希用当前 bcrypt API 生成。

这个选择有意绕过注册链：

- 本测试的起点是“已有 admin 凭据登录”，不需要让注册行为参与失败原因。
- 如果通过注册创建用户，还要额外改变 role 或依赖注册默认值，会增加与本题无关的耦合。
- fixture 的明文密码必须满足当前至少 15 字符的业务规则，避免测试数据与真实契约脱节。

### 3.3 为什么使用独立测试文件

新测试放入 `week2-express/src/__tests__/auth-flow.test.js`，独立拥有数据库生命周期。

取舍：

- `monthly-sales.test.js` 重点验证聚合结果与权限门禁；新文件重点验证登录签发结果与后续链路的衔接。
- 新测试不需要订单 fixture，复用报表文件会引入无关数据。
- 文件边界能改善测试意图和失败定位，但不能单靠文件位置断定根因；原有“直接 token → 报表 200”仍是重要对照。
- 独立 `MongoMemoryServer` 有额外启动成本。当前使用 `--runInBand`，不能假设测试文件并行或整体一定更快；本次接受的是职责清晰度，而不是未经测量的性能结论。

### 3.4 最小但充分的断言

| 断言 | 证明内容 | 删除后的代价 |
|---|---|---|
| 登录响应 `200` | 已有凭据通过查询和 bcrypt 比较，签发过程没有把请求变成失败响应 | 后续失败仍可能暴露问题，但难以迅速判断是否在登录阶段已经失败 |
| `body.payload.accessToken` 是非空字符串 | Controller / Service 当前响应形状中确实交付了 token | 资源请求出现 `401` 时，难以区分“没有产出 token”和“验证链拒绝 token” |
| 携带该 token 请求报表返回 `200` | 登录签发结果能通过 token 验证、数据库角色查询和资源处理 | 删除后就失去本测试的核心目标 |

不重复断言报表聚合数值。报表逻辑仍可能令第三项失败，因此需要结合原有报表测试作对照，而不能把所有失败都归因于 JWT。

## 4. 集成测试生命周期

独立测试文件拥有以下状态：

| 状态 | 创建 / 设置 | 使用范围 | 清理 / 恢复 |
|---|---|---|---|
| `JWT_SECRET` | `beforeAll` 保存原值，并无条件覆盖为固定测试密钥 | 整个 suite | `afterAll`：原值为 `undefined` 时删除，否则精确赋回原值 |
| `MongoMemoryServer` | `beforeAll` 启动 | 整个 suite | `afterAll` 停止实例 |
| Mongoose 连接 | 内存库启动后建立 | 整个 suite | `afterAll` 先断开连接 |
| admin fixture | 连接建立后创建 | 两个测试只读共享 | 随内存数据库销毁，不单独删除 |

当前不需要 `beforeEach`：两个测试没有修改 admin fixture，第二个测试创建的新用户不会改变第一个测试依赖的状态。若以后增加修改共享用户的场景，应重新评估隔离粒度，不能机械沿用 `beforeAll`。

`JWT_SECRET` 的关键纠错：

- `--runInBand` 下多个测试文件可能在同一个 Jest 进程中依次运行，测试文件结束不等于进程结束。
- 只在 secret 缺失时赋值会令结果依赖外部环境或前置 suite。
- 因此测试必须“保存 → 固定覆盖 → 精确恢复”，同时处理原值未定义、合法和非法三种状态。
- 强制终止进程时 hook 不能保证执行；本设计只承诺正常 Jest 生命周期内的隔离。

## 5. 第二条认证链：新注册用户 → 报表 403

### 5.1 最终选择的契约

本测试保护的是：

> 新注册用户登录后不能访问 admin 报表。

它不额外保护“注册一定把 `role` 持久化为 `member`”。因此不直接查询数据库断言 `role === 'member'`。

这样取舍的原因：

- 最终 `403` 足以证明当前登录用户没有 admin 报表权限。
- 如果默认角色意外变为 admin，请求会变成 `200`，测试能够发现严重回归。
- 如果默认角色从 member 改成另一个非 admin 值，本测试仍通过；精确默认角色属于另一个持久化契约，应由单独测试保护。
- 直接查询 `role` 会提供更具体证据，但也让这条外部行为测试耦合数据库字段与内部模型。

### 5.2 三阶段输入输出

```text
POST /auth/register
输入：name / email / 满足长度规则的 password
输出：201，注册数据位于 body.data

POST /auth/login
输入：上一阶段的 email / 明文 password
输出：200，token 位于 body.payload.accessToken

GET /reports/monthly-sales
输入：Authorization: Bearer <真实登录所得 token>
输出：403，body 为 { error: '权限不足' }
```

### 5.3 `403` 的证据边界

能够证明：

- 注册得到的用户可以通过真实登录取得 token。
- token 被 `validateToken` 接纳，否则更可能停在 `401`。
- 请求到达授权判断并被作为非 admin 拒绝。
- 登录、认证与授权三段能够按当前契约串联。

不能单独证明：

- 数据库中的角色精确等于 `member`；`member`、`null` 或其他非 admin 值都可能落入同一个拒绝分支。
- 报表聚合逻辑正确；请求在进入报表业务逻辑前已被授权中间件拦截。
- 其他资源或其他角色的权限规则正确。

术语边界：这仍是后端集成测试，不是包含前端和外部依赖的完整 E2E。

## 7. 错误、纠正与长期提醒

### 错误 1：用新需求替代当前覆盖排序

一开始选择登录限流，但这引入了 Redis、阈值、`429` 和降级策略等不存在的契约。以后做覆盖地图时，必须先分开：

```text
当前行为的回归保护
vs
值得新增的产品 / 安全能力
```

### 错误 2：把非空字符串当作有效 JWT 证据

token 是非空字符串只证明响应形状。真正的有效性来自它被受保护路由接纳并形成预期的 `200` 或授权阶段 `403`。

### 错误 3：把 `403` 过度解释为精确角色证据

共同结果只能证明共同分支。多个非 admin 角色都返回相同 `403` 时，不能从响应反推数据库中一定是 `member`。

### 错误 4：忽略进程级环境变量污染

Jest hook 的边界是 suite，不是 shell 进程。共享 `process.env` 必须显式恢复，不能假设测试文件结束后环境自动消失。

### 本日保留的思维模型

```text
先定义要保护的外部契约
→ 选择最小 fixture，主动排除无关链路
→ 每条断言说明它增加了什么证据
→ 用已有测试建立对照，缩小失败范围
→ 明确最终状态码不能证明什么
```
