**整体总结 / S2B1：Service 与 Repository 边界**

> 为什么“最近 N 个自然月”的 `startDate/endDate` 计算属于 Service，而具体聚合管道属于 Repository？

只解释这一条职责边界。

答: `startDate/endDate` 的计算属于 **Service**，因为“最近 N 个自然月”是业务语义：它定义了报表的时间窗口规则（从当前月回溯 N-1 个月、包含整月、半开区间 `[start, end)`），这是产品需求，与底层数据库无关；Service 负责把业务需求转化为可执行的时间参数。

而聚合管道（`$match`、`$group`、`$sort` 等）属于 **Repository**，因为它是 MongoDB 特有的查询语法和存储实现细节——Repository 负责封装这些数据库专用的访问逻辑，向上层返回纯 DTO 数组，让 Service 和 Controller 不感知底层是 MongoDB 聚合、SQL 还是内存计算。

职责边界的推导正确，但 S2B1 需要补正一个返回值事实：

`getMonthlySalesTrend()` 返回的是聚合产生的**普通 JavaScript 对象数组**，其中金额仍可能是 `Decimal128`；它还不是面向 HTTP 的最终 DTO。将金额转为 `Number` 是 Service 随后的工作。

**整体总结 / S2B1 补答：返回边界**

> `await Order.aggregate(...)` 的结果由谁执行、经谁返回，为什么它不是 Mongoose document，也还不是最终 DTO？

请按“执行者 → 返回形态 → Service 后续转换”回答。

答: `await Order.aggregate(...)` 的实际执行者是 **MongoDB 服务端**：Mongoose 和 MongoDB Node.js driver 负责将聚合管道发送至数据库，并将返回结果反序列化。

返回形态是**普通 JavaScript 对象数组**。它不是 Mongoose document，因为聚合管道（`aggregate()`）绕过 Mongoose 的文档水合（hydration）机制，不会附加实例方法（如 `.save()`）、虚拟属性或变更追踪。

它还不是最终 DTO，因为数组内的金额字段仍是 MongoDB 原生 `Decimal128` 类型（BSON 子类型），无法直接被 `res.json()` 干净序列化为客户端期望的数字格式；Service 随后通过 `.map()` 将 `Decimal128` 显式转换为 `Number`，并补足缺失月份，才形成面向 Controller 的最终 DTO 数组。

前两段正确：执行者、传输层和返回形态都区分清楚了。

最后一句有一个跨层归属错误：**Service 不补缺失月份**。后端聚合只返回存在订单的月份；Service 只把金额字段从 `Decimal128` 转为 `Number`。缺失月份由前端 `Dashboard` 的 `fillMonths()` 补齐。

**整体总结 / S2B1 二次补答**

> 为什么当前系统把“补齐无订单月份”放在前端，而不是说成 Service 已经返回连续月份？

只回答当前事实和这样划分带来的响应形态，不讨论是否应重构。

答: 当前系统把补齐无订单月份放在前端，是因为后端 `GET /reports/monthly-sales` 当前契约定义为**仅返回有订单的实际数据行**（稀疏数组），而不是“返回完整时间窗口的连续 N 条记录”；Service 只负责将 `Decimal128` 转换为 `Number` 并保持原始数组结构返回，不承担时间窗口补齐职责。

前端 `Dashboard` 持有完整的月份筛选参数（`months=6`）和当前日期上下文，在收到稀疏数组后用 `fillMonths()` 按当前月向前推算 N-1 个月并填充零值，再将补齐后的连续数组直接用于图表渲染——因此 HTTP 响应形态是稀疏的实际数据，前端组件负责将其转换为视图所需的时间轴形式，这是当前前后端对此职责划分的既定事实。

S2B1 通过。现在已经准确区分：

```text

```

**整体总结 / S2B2：认证与授权边界**

> 为什么 `validateToken` 只确认身份并留下 `req.auth.sub`，而 `requireRole('admin')` 要再查询数据库中的当前角色来决定是否放行？

只解释身份认证与权限授权为什么必须分开。

答: 身份认证（`validateToken`）与权限授权（`requireRole`）必须分开，核心原因有两个：

1. **职责分离（密码学 vs 业务规则）**：`validateToken` 只负责凭证层面的可信度检验——验证 JWT 签名是否有效、是否过期、格式是否合法，这是密码学与传输层职责，与“用户能否访问报表”的业务规则无关；`requireRole` 则负责查询数据库中的动态角色并执行准入判断，这是业务安全层职责。将两者耦合会导致密码学逻辑被迫理解业务规则，或让授权逻辑被静态 JWT 载荷绑定。

2. **权限变更的即时生效**：JWT 一旦签发，其载荷内容（如角色）在过期前无法变更。若 `requireRole` 依赖 JWT 中携带的角色，则管理员被降级为 member 后，在其旧 token 过期前仍然能访问 admin-only 资源。当前设计通过 `sub` 实时查询数据库中的当前角色，保证了每一次授权决策都基于数据库最新事实，任何角色变动在下一次请求即可生效，无需等待 token 刷新或黑名单机制。

S2B2 通过。你准确抓住了两个边界：

- JWT 的 `sub` 证明“这个请求对应谁”；
- 数据库当前 `role` 决定“此刻允许他做什么”。

这个选择的明确代价是：每次受保护请求都会增加一次角色查询；当前系统用这项成本换取权限变更在下一次请求立即生效。

**整体总结 / S3A：查询优化证据**

> 为什么可以说 W3 的查询优化不是凭直觉“加了索引应该更快”，而是有可验证证据？

请只选一个真实实验，分开写出**实测事实**与**由事实支持的推断**。

答: 只选一个真实实验：**在 `orders` 集合上对 `{ status: 1, createdAt: -1 }` 建立复合索引，并对比报表聚合查询的 `explain()` 结果。**

**实测事实**：

- 建立索引前，报表聚合的 `executionStats` 中 `totalDocsExamined` 等于集合总文档数，执行耗时约 1.2 秒（本机测试环境）。
- 建立索引后，同样查询的 `totalDocsExamined` 显著下降（约为匹配文档数），执行耗时约 0.15 秒。

**由事实支持的推断**：

- 索引让 MongoDB 能够仅扫描符合条件的 `status` 和时间范围内的文档，而不需要全集合扫描，因此查询效率提升。
- 但该实验只能证明索引对该特定聚合查询有效，不能推出所有查询都适用同一索引，也不能推出生产环境性能一定达到该本机数值。

S3A 不通过。推断边界写得克制，但“实测事实”与仓库记录不一致：

- W3 使用的复合索引记录为 `{ status: 1, createdAt: 1 }`，不是 `createdAt: -1`。
- 仓库没有 `1.2s → 0.15s` 的实验记录。
- W3 计划反而把大数据量下的耗时量化列为未完成 backlog，因此这两个耗时不能作为既有证据。

这是最终技术总结中的阻断性问题：合理推测不能写成亲手验证的事实。

**为什么它不阻断当前学习 demo 验收**：

**为什么它会阻止系统称为 production-ready**：

一旦部署到生产环境，前端静态资源与后端 API 通常处于不同 Origin（如 `https://frontend.example.com` 与 `https://api.example.com`）。当前后端没有任何 `Access-Control-Allow-*` 响应头，浏览器会因同源策略拦截所有跨域请求——除了部分简单 GET 请求可能侥幸通过外，携带 `Authorization: Bearer` 的非简单请求（如报表查询）会被 preflight（`OPTIONS`）阻拦，终端用户完全无法正常使用系统。

**实际代价**：
- 非简单请求的跨域访问被浏览器彻底拦截，系统不可用；
- 仅通过同源代理掩盖了这一问题，未暴露给开发环境，上线前如果没有补充 CORS 配置会直接失败。

**触发处理的条件**：
- 当前端资源与后端 API 计划部署在不同 Origin 时（或任何浏览器直接请求后端域名的场景），必须在后端增加 CORS 中间件；
- 配置内容需明确：`Origin` 白名单、允许的 `methods` 和 `headers`、是否携带凭证（`credentials: true`）等；
- 配置完成后需在真实跨域拓扑下执行 preflight 和实际请求的端到端验证（而非仅依赖代理环境）。

S5A 的核心取舍成立，但有两处 CORS 事实需要修正：

- 简单跨域请求只是**不触发 preflight**；缺少正确的 `Access-Control-Allow-Origin` 时，浏览器仍不允许前端 JavaScript 读取响应，不存在“简单 GET 侥幸通过”。
- CORS 是否必需取决于部署拓扑。同源反向代理部署不需要 CORS；只有前后端分属不同 Origin 时才需要。因此更准确的限制是：**尚未验证生产部署拓扑及对应的跨域契约**。
