## 1. 判据：哪些内容做成板，哪些不做

沿用 `visualization-optimization-roadmap.md` 2026-08-18 补的肯定面（同类对象 ≥3 个要相互比较、
差距本身是结论、信息有序或分层要用位置编码）。筛下来：

**做成板（六块）**

| 块 | 为什么图更好 | 复用的形态 |
|---|---|---|
| ① 中间件管道 | 六行输出的顺序本身就是结论，缩进即调用栈深度 | `framePlayer` 逐帧 |
| ② 四层职责 | 四层 × 碰什么 / 不碰什么，是二维判断 | 表格 + 位置编码 |
| ③ 一条请求穿四层 | 形状逐格变化，与 W3 pipeline 同构 | `w3-pipeline-strip` 的同型条带 |
| ④ 两条互斥路径 | 两条路径并排才看得出「触发方式不同」 | 并排卡片 + 纠错三段式 |
| ⑤ 错误翻译落层 | 七类原始错误 × 翻译点 × 领域错误 × 状态码 | 矩阵 |
| ⑥ 归属判断标尺 | 四段逻辑各自归属，靠一把尺子分开 | 矩阵 + 纠错三段式 |

**明确不做**

- **CRUD 与更新操作符速查**（`$set` / `$inc` / `$push`）：没有比较价值，roadmap 明确禁止「为少量数字出图」。原文接进笔记 tab 即可。
- **优雅关闭时序单独成块**：机制清楚但只有一条线性顺序，图形收益不足；更划算的做法是并进 W9 板讲「应用层 SIGTERM 处理 ↔ systemd 契约」两端，本次未做，留作候补。
- **Mongoose 两层防线单独成块**：信息量不足以撑一块，并进 ⑤ 作为一节——它正是 repository 里两个 catch 分支并存的原因。

## 2. 事实口径：以当前代码为准，笔记作为推理来源

W1–W2 的笔记写于 7 月初，`week2-express/src` 此后经历了 W4 认证、W9 上线、W10 日志三轮改动。
本板的规则是：**结论以当前代码为准，笔记提供推理与踩坑过程；两者不一致时按代码写，
并在 evidence 或结论口径里点出差异**，不让展板复述已经被改掉的写法。

执行时命中三处差异：

| 处 | 笔记记的 | 当前代码 | 处理 |
|---|---|---|---|
| `app.js` 错误分派 | Day3 §3.5(b) 决定改用 `instanceof` | `switch (err.constructor)` | 板上按当前代码陈述，并在结论口径里说明：现有错误类之间没有继承关系，两种写法对这 6 个类结果相同；差异另记进开放问题清单 |
| controller 的 id 校验 | Day2 §8.2 的 `if (id && isNaN(parseInt(id)))` | 已被 `validateIdParam` 中间件取代（Day4 §8 的重构） | 板上画当前形态；`parseInt` 那版不上板 |
| `req` / `res` 只在 controller | Day2 §1.2 的越界尺子 | 仍成立，但 `config/logger.js` 里有 `req.body.password` 等脱敏路径**字符串** | evidence 写明这是字段路径字符串、不是对请求对象的访问 |

第一条已进 `w2Topics.ts` 的 `W2_OPEN_ITEMS`，状态「待澄清」：**在没有子类之前不影响行为，
不单独记 DEBT**，回看时确认是有意改动还是漂移。

## 3. W1 的三块挂在数据库板，不新开 tab

建模、最左前缀、覆盖查询都是数据库内容，另开一个 W1 tab 会把同一主题切成两页。
做法是把数据库板从 5 个知识点扩到 8 个，标题改为「MongoDB 建模、聚合与查询优化」，
顺序按概念递进重排为三段：

```text
先存对   ① 建模决策（W1）
再写对   ② 聚合分层  ③ pipeline 形状  ④ 自然月边界（W3）
最后调快 ⑤ explain 三数  ⑥ 最左前缀（W1）  ⑦ 覆盖查询（W1）  ⑧ $lookup 外键索引
```

**样本边界必须与图相邻**：W1 的索引实验跑在 mongosh 手工造的 `bigdata` 集合（50000 文档、
city 三取值），W3 的实验跑在项目的 `orders` / `users` 上。⑥⑦ 两块各挂一条结论口径说明这一点，
`verify:board` 有两条断言守着「bigdata」「50000」这两个词出现在页面上——
少了这句，16667 这个数字会被读成项目数据。

## 6. 这块板的验收句

不读正文也能当场答出下面六句，答不出就是没做到：

1. 三个中间件各在 `next()` 前后打印一行，输出顺序是什么？为什么离开是反序？
2. logger 的计时结束点放在 `next()` 之后会量到什么？放在 `res.on('finish')` 里呢？
3. `req` / `res` 可以出现在哪几层？依据是什么？
4. `GET /users/:id` 的三种结局（400 / 404 / 200）各自停在哪一层？
5. 404 和 409 是不是同一条响应路径？各自由谁调用 `res`？
6. 「用户允许更新哪些字段」该放中间件还是 service？用哪把尺子判断？
