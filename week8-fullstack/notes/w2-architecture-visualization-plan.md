## 1. 判据：哪些内容做成板，哪些不做

沿用 `visualization-optimization-roadmap.md` 2026-08-18 补的肯定面（同类对象 ≥3 个要相互比较、
差距本身是结论、信息有序或分层要用位置编码）。筛下来：

**做成板（六块）**

> 下表「复用的形态」一列记的是第一轮的选型。其中 ①③⑤ 三块的形态在同日被判定不合格并返工，
> 现行形态见 §7；此处保留原判断留痕。

| 块 | 为什么图更好 | 复用的形态（第一轮） |
|---|---|---|
| ① 中间件管道 | 六行输出的顺序本身就是结论，缩进即调用栈深度 | `framePlayer` 逐帧 |
| ② 四层职责 | 四层 × 碰什么 / 不碰什么，是二维判断 | 表格 + 位置编码 |
| ③ 一条请求穿四层 | 形状逐格变化，与 W3 pipeline 同构 | `w3-pipeline-strip` 的同型条带 |
| ④ 两条互斥路径 | 两条路径并排才看得出「触发方式不同」 | 并排卡片 + 纠错三段式 |
| ⑤ 错误翻译落层 | 七类原始错误 × 翻译点 × 领域错误 × 状态码 | 矩阵 |
| ⑥ 归属判断标尺 | 四段逻辑各自归属，靠一把尺子分开 | 矩阵 + 纠错三段式 |

**明确不做**

- **CRUD 与更新操作符速查**（`$set` / `$inc` / `$push`）：没有比较价值，roadmap 明确禁止「为少量数字出图」。原文接进笔记 tab 即可。
- **优雅关闭时序单独成块**：机制清楚但只有一条线性顺序，图形收益不足；更划算的做法是并进 W9 板讲「应用层 SIGTERM 处理 ↔ systemd 契约」两端，本次未做，留作候补。
- **Mongoose 两层防线单独成块**：信息量不足以撑一块，并进 ⑤ 作为一节——它正是 repository 里两个 catch 分支并存的原因。

## 7. 返工：把四块从表格改成流动图（同日）

### 起因

第一轮交付后本人指出「看截图没有什么动效和图表，像 express 四层分层数据怎么流转、
mongodb 聚合这些不是很适合做成可视化吗」。

核对后确认这条成立，而且**第一轮违反的是仓库自己的判据**：`visualization-optimization-roadmap.md`
第八轮（2026-08-18）已经把验收标准改成「**遮住这块板的标题与结论段，仍能答出它的验收句**」，
并把「图形只负责关系」改成「**图形负责结论本身**」。第一轮六块里有四块是表格加正文：

| 块 | 第一轮形态 | 遮住标题后能不能答出验收句 |
|---|---|---|
| ① 中间件管道 | 缩进的文字日志 | 否——「为什么离开是反序」全靠读注解 |
| ③ 请求穿四层 | 六列卡片，六格同时铺开 | 否——看不出下行与上行，也看不出这是一个来回 |
| ⑤ 错误落层 | 七行五列的表 | 否——「所有错误从一个出口出去」这条结论没有版面 |
| ⑥ 归属标尺 | 四行矩阵 | **是**——四段逻辑 × 两类归属本来就是二维判断，表是对的编码 |

顺带确认 W3 的聚合 pipeline 块也是同一问题：六张卡片描述 input / output，
但「阶段顺序改变数据形状」这条结论要靠读文字还原。

### 改了什么

1. **① 三层同心环 + 一枚令牌**。A / B / C 画成真正嵌套的三个环，令牌进入时走左半、
   离开时走右半，从最外层进到最内层再原路退出。包裹结构由几何直接给出。
   文字日志保留在下方——读屏用户与需要精确核对的人不依赖图形。
2. **③ 双轨流动图**。六条泳道（Router / 校验中间件 / controller / service / repository / MongoDB），
   左边是下行轨、右边是上行轨；令牌带着**这一跳携带的数据形状**沿轨道走完一个来回，
   走过的轨道段留色，所以静止的截图上也看得出「下行到底、再原路返回」。
   三种结局是同一条轨道上的三个停止点：400 停在校验中间件，404 与 200 都停在 controller。
   数据结构相应改成 `actors` + `steps{actor, leg, carries}`，把「携带什么」升成一等字段。
3. **⑤ 汇聚 → 单一出口 → 扇出**。原始错误按翻译点所在的层分三列，
   全部汇进 `app.js` 那个四参数中间件，再扇出成 400 / 401 / 403 / 409 / 500 五个出口。
   七行明细表降为可折叠的「逐行明细」：图给结论，表给每一格的出处。
4. **W3 ③ 文档形状逐阶段变形**。每一步并排画出「前一阶段之后」与「这一阶段之后」两张文档卡，
   字段用芯片表示，状态四色编码：`added` 新生成、`dropped` 这一步消失（划掉）、
   `changed` 形状变了、`kept` 原样带下去；卡片底部单列一行**多重性**
   （一条 = 一个订单 → 一条 = 一个用户）。字段清单逐行读自
   `repositories/users.js` 的 `getCustomerSpending()`，不是示意图。

**② 与 ⑥ 保持表格不变**：这两块是二维分类判断（四层 × 碰什么 / 不碰什么、
四段逻辑 × 两类归属），矩阵就是 roadmap 肯定面里说的正确编码，改成流程图反而失真。

### 新增的结构断言

图形承载结论之后，「图塌了」就等于「结论没了」，所以这几条必须有机器断言守着：

```text
架构板 洋葱三层环 / 洋葱令牌在场 / 洋葱环逐层内缩（宽度严格递减）
架构板 六条泳道 / 令牌在场 / 走过的轨道已着色（.arch-flow-rail.on ≥ 6）
架构板 错误唯一出口（hub 只能有一个）/ 状态码扇出五格
W3 聚合 六段管道轨道 / 前后两张文档卡 / $group 那步同时有 added 与 dropped 芯片
```

`prefers-reduced-motion` 下令牌与轨道的位移动画全部关闭，位置仍然正确。
`verify:board` 从 570 升到 **581/581**。
