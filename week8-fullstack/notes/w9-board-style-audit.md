# W9 展板样式一致性诊断（字号 / 柱形几何）

> 时间：2026-08-18（Asia/Shanghai）
> 范围：`week8-fullstack/src/frontend/` 的 W9 部署板（`W9Board.tsx` + `styles.css` 的 `.w9-*` 段 + `charts.tsx`）
> 性质：**只诊断，未改任何样式**。下面每条都有实测数字或行号，不是观感描述。
> 复现：`yarn build:showcase` 后用 playwright 量渲染后的 computed style 与 getBoundingClientRect，
> 视口取 1440 / 1100 / 390 三档，`deviceScaleFactor=1`。

---

## 0. 一句话结论

问题不在"某几个地方写错了字号"，在于**同一块板上并存四套互不通气的尺寸体系**：

| # | 体系 | 谁在用 | 断点响应 |
|---|---|---|---|
| A | `--fs-s1…s7` 字梯子（7.5–10.5px） | 256 处 `.w9-*` 声明 | ≤720px 整体抬高；≥1200px **无** |
| B | 硬编码 px（11 / 12 / 12.5 / 13 / 14…） | 122 处 `.w9-*` 声明 | 两个断点**都不响应** |
| C | SVG viewBox 用户单位（`charts.tsx`） | 2 个图表块 | 随容器宽度**无级缩放**，与断点无关 |
| D | UA 默认字体族 | 全部 `button` 及其子节点 | 与体系无关 |

结果是：**桌面上 W9 板的正文比手机上还小，而板里唯一的柱状图文字比正文大一倍、比 h3 标题还大。**

---

## 1. 最严重：SVG 图表脱离页面尺寸体系（视觉上最刺眼的那一条）

### 事实

`charts.tsx` 的 `HBarChart` 固定写 `width = 640`，`viewBox="0 0 640 H"`，
而 `styles.css:274` 是 `.chart-wrap svg { width: 100%; height: auto; display: block; }`。
于是 **SVG 内部的一切长度单位（含 `font-size`）都被 `容器宽/640` 这个比例整体缩放**。

实测（`topic=release` 的 `VerifyCoverageChart`、`topic=identity` 的 `SnagChart`，两者数字一致）：

| 视口 | SVG CSS 宽 | 缩放比 | 柱厚（设计值 18） | 轴文字（CSS 声明值） | 轴文字（实际渲染） |
|---|---|---|---|---|---|
| 1440px | 1346px | **2.103×** | **37.9px** | 10px | **21.0px** |
| 390px | 336px | **0.525×** | **9.4px** | 11.5px | **6.0px** |

同一张图，文字从 6.0px 变到 21.0px，跨度 **3.5 倍**；柱子从 9.4px 变到 37.9px，跨度 **4.0 倍**。
同一屏上的 HTML 正文在这两个视口只有 11.5px ↔ 10.5px 的变化。

### 三个连带后果

1. **写在 CSS 里的修复没有生效，但注释以为它生效了。**
   `styles.css:4099-4103` 有一条针对性覆盖，注释原文写着"桌面回到 10px"：
   ```css
   .w9-chart-block .tick-text { font-size: var(--fs-s6); }
   .w9-chart-block .value-text { font-size: var(--fs-s6); }
   ```
   桌面实测是 **21.0px**，不是 10px。因为覆盖改的是用户单位，缩放在它之后发生。
   这条覆盖只把问题从"11 用户单位"挪到"10 用户单位"，量级没动。

2. **手机端的字梯子抬升在这里帮了倒忙。**
   ≤720px 把 `--fs-s6` 从 10px 抬到 11.5px，本意是给元信息一个可读下限；
   但乘上 0.525 之后是 6.0px，仍然远低于板上任何其它文字（手机端最小 9px 档）。
   抬升在 SVG 里被稀释成了看不见的 0.8px。

3. **量级关系被反转。** 桌面上轴标签 21px > 板块标题 h3 的 22px 几乎持平，
   远大于正文 12.5px；手机上同一批文字又变成全板最小。同一个元素在两个视口
   处在视觉层级的两个极端 —— 这是"字体不统一"最直接的来源。

`charts.tsx:2-4` 的规格注释写的是"细 mark（柱 ≤24px）"。桌面 37.9px 已经违反自己的规格。

## 2. 板上并存三套"柱"，几何约定互不相干

W9 板里有三种柱形，各自用完全不同的方式决定大小，也各自用不同的方式响应断点：

| 柱 | 定义位置 | 桌面 1440 实测 | 手机 390 实测 | 缩放方式 |
|---|---|---|---|---|
| SVG 横条（HBarChart） | `charts.tsx:205` `barH = 18` | 厚 **37.9px** | 厚 **9.4px** | 随容器宽无级缩放 |
| `.w9-spoken-bar` 竖柱 | `styles.css:3569-3570` | **93 × 84px**（宽随 8 等分列走，高固定 84） | **42 × 56px** | 高度靠 `@media` 一次性跳变（84→56） |
| `.w9-mem-seg` 横条 | `styles.css:3199` | 高 **46px** 固定 | 高 **58px**（`styles.css:4056` 反而调大） | 高度靠 `@media` 跳变，且方向与上一条相反 |

三条各自都说得通，放在同一块板上就没有可比性了：读者无法从"柱子更粗"推出任何含义，
因为粗细同时被"哪种柱"和"当前视口宽度"决定。另外 `.w9-mem-seg` 在手机上变高、
`.w9-spoken-bar` 在手机上变矮，方向相反，没有统一的密度取向。

## 3. 字梯子只覆盖"元信息"，正文全是硬编码 px

`--fs-s1…s7` 的取值是 7.5–10.5px（`styles.css:33-39`），设计定位是标签、脚注、chip 这类小字。
正文层（12–16px）**没有 token**，只能逐处写死。实测 `.w9-*` 段（styles.css 2808–4116）：

```
token  --fs-s6  ×131   --fs-s7  ×94   --fs-s5  ×22   --fs-s4  ×9      = 256 处
硬编码 12.5px ×82   13px ×12   12px ×10   14px ×7   15px ×3
       11px ×2   24/20/19/18/16/13.5px 各 ×1                          = 122 处
```

122 处硬编码里，**12.5px 一个值占了 82 处**——说明事实上存在一个"W9 正文号"的约定，
只是它没有名字、没有 token，所以每次新写一段就有一定概率写成 12px 或 13px。

渲染侧的后果（1440px，13 个专题全量扫描，3447 个可见文本节点）：

```
一块板上出现 17 档字号：29 / 22 / 20 / 16 / 15 / 14 / 13.5 / 13 / 12.5 / 12 / 11.5 / 11 / 10.5 / 10 / 9.66 / 9.5 / 9
```

按语义角色拆开看，同角色的档数是这样的：

| 角色 | 档数 | 实测分布 |
|---|---|---|
| `h3` 板块标题 | 1 | 22px ×48 ✅ 唯一整齐的一类 |
| `p` 段落 | 5 | 16px / 12.5px / 12px / 10.5px / 10px |
| `strong` | **10** | 20 / 16 / 15 / 14 / 13 / 12.5 / 12 / 11 / 10.5 / 10px |
| `code` | **8** | 14 / 13.5 / 12.5 / 11.5 / 10.5 / 10 / 9.66 / 9px |
| `button` | 6 | 15 / 14 / 12.5 / 12 / 11.5 / 10.5px |
| `small` | 4 | 10.5 / 10 / 9.5 / 9px |
| `em` | 4 | 10.5 / 10 / 9.5 / 9px |

`p` 里出现 10.5px、`strong` 里出现 10px，意味着**正文级元素掉进了元信息级字号**，
这不是层级设计，是漏网。

### 3.1 `code` 的 8 档另有具体成因

`code` 被两条规则同时管：

- `styles.css:1630` 全局 `code { font-size: 0.92em; }` —— 相对父级
- 各处 `.w9-xxx code { font-size: 12.5px }` 等 —— 绝对值

于是没被局部覆盖的 `code` 会跟着父级浮动：父级 10.5px 时是 `10.5 × 0.92 = 9.66px`
（实测确实出现 9.66px ×17）。同一段代码片段在不同卡片里大小不同，且出现了非整数字号。

## 4. W9 板没有桌面档，所以桌面比手机还小

`styles.css` 用 `@media (min-width: 1200px)` 做"桌面阅读模式"，给各板整体抬字号。
各板拿到的份额差得很远：

| 桌面档位置 | 覆盖的板 | 规则条数 | 其中带 font-size |
|---|---|---|---|
| `styles.css:1862` | 全局 + W5 + W6 + authk + notes | 310 | **208** |
| `styles.css:2265` | auth-master（W4 代表页） | 20 | 13 |
| `styles.css:2587` | 面试板 `iv-*` | 11 | 9 |
| `styles.css:2799` | W6 Day4 `d4-*` | 7 | 6 |
| `styles.css:4077` | **W9 `w9-*`** | 4 | **3** |

W9 一共有 **914 条 `.w9-*` 规则**，桌面档只照顾到 3 条（`.w9-node > p`、`.w9-matrix-cell`、
`.w9-rule-branches p`）。而 ≤720px 的手机档会把 `--fs-s*` 整体抬高，`.w9-*` 有 256 处吃这个梯子。

**净效果是尺寸曲线反了**。实测同一份产物、切换 tab 直接对比：

| 视口 | W9 部署板 `p` 中位数 | W6 测试板 | W5 运行时板 | W4 认证板 | 面试板 |
|---|---|---|---|---|---|
| 1440px | **10.5px** | 11.5px | 16px | 14px | 14px |
| 1100px | **10.5px** | 11.5px | 14px | 11.5px | 12px |
| 390px | **11.5px** | 11.5px | 14px | 11.5px | 12px |

两条读法：

1. **纵向**：W9 板在 1440px 桌面上的正文（10.5px）比 390px 手机上（11.5px）**更小**。
   屏幕越大字越小，与全站其它板的方向相反。
2. **横向**：1440px 下同一个展板里切 tab，正文从 10.5px（W9）跳到 16px（W5），**差 1.52 倍**。
   这是"从别的板切到 W9 就觉得字变小了"的实测来源。

## 5. 所有按钮及其子节点用的不是 system-ui，是 Arial

`styles.css:63` 只给 `body` 设了 `font-family: system-ui, -apple-system, "Segoe UI", sans-serif`。
`button`（`styles.css:120`）和 `input, select`（`styles.css:112`）**没有 font-family 声明**，
表单控件不继承 `body` 的字体族，落回 UA 默认（Chromium 是 Arial）。

实测 1440px，13 个专题共 3447 个可见文本节点：

```
system-ui   2542 个
Arial        827 个   ← 全部是 button 及其后代
ui-monospace  78 个
```

W9 板恰恰把大量正文塞进按钮里（`.w9-overview-row`、`.w9-path-switch`、`.w9-acc-row`、
`.w9-port-chip`、`.w9-spoken-layer`、`.w9-fix-item button`…），所以受影响面积很大：
同一行里"标签在按钮内 = Arial、说明在按钮外 = system-ui"。在 macOS / Windows 上
system-ui 分别是 SF Pro / Segoe UI，与 Arial 的字重、字宽、数字形状差别明显，
中文回退链也不同。**这一条是"字体不统一"里唯一真正的"字体族"问题**，其余都是字号问题。

## 6. 不建议动的地方（避免把诊断做成一刀切）

- **h3 只有一档（22px）**：唯一已经整齐的层级，不要动。
- **`.w9-spoken-bar` 的"零错画成贴地虚线"**：那是刻意的语义编码（`styles.css:3572`），
  统一柱形几何时必须保留这个变体。
- **`--fs-s*` 在 ≤720px 抬高**：方向是对的，问题在于桌面侧没有对称的一档，
  以及正文层没进梯子——不是这条抬升本身有错。
- **`.w9-chart-block` 的底色/边框与 W9 卡片族一致**：这一层已经统一，问题只在 SVG 内部。

## 7. 修复优先级（下一轮做，本轮不动代码）

| 优先级 | 问题 | 影响面 | 备注 |
|---|---|---|---|
| P0 | §1 SVG 缩放 | 2 个图表块，桌面/手机各一个极端 | 需要让 SVG 不再整体缩放（固定用户单位 = CSS px），而不是继续在用户单位里调数值 |
| P0 | §4 缺桌面档 | 914 条规则里 256 条受影响 | W9 是全站唯一没有 ≥1200px 档的板 |
| P1 | §5 按钮字体族 | 827 个节点 | 一行修复：把 `button, input, select` 并进 `font-family: inherit` |
| P1 | §3 正文层无 token | 122 处硬编码 | 需要先给 12.5px 这个事实约定一个名字 |
| P2 | §2 三套柱几何 | 3 处 | 统一前要先决定"柱粗细"在这块板上到底编码什么 |
| P2 | §3.1 `code` 8 档 | 70 处 code 节点 | 全局 `0.92em` 与局部绝对值二选一 |

## 8. 诊断怎么复现

```bash
cd week8-fullstack/src/frontend
yarn install && yarn build:showcase
# 需要 playwright（本仓库不入 devDependencies，全局装即可）
node <诊断脚本>   # 见本轮会话；核心是遍历 13 个 topic，
                  # 采集 computed fontSize / fontFamily 与 getBoundingClientRect
```

关键采样点：13 个 topic × {1440, 1100, 390} 三档视口；
只统计"自己直接包含非空文本节点"的元素，避免把容器的继承字号重复计入。
