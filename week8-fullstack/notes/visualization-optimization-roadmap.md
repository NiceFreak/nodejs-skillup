## 目标与约束

这轮优化的目标不是增加装饰，而是让用户更快判断：

1. 调用或事件按什么顺序发生。
2. 线程、组件、层和资源分别负责什么。
3. 成功路径与失败路径在哪里分叉。
4. 实验结果能证明什么、不能证明什么。
5. 测试覆盖如何互补，状态和资源如何随时间变化。

实施时继续遵守以下边界：

- 优先复用现有 React、CSS、hash URL、`demo/review` 状态与专题数据，不引入图表框架或新的全局状态层。
- 不把增加卡片、图标、阴影或颜色当作可视化成果。
- 不为少量数字创建没有比较价值的统计图。
- 图形只负责关系；原始结论、测试条件、未测量项和来源仍保留文字。
- Markdown 长文继续以阅读为主，不大规模重写现有前端。
- 每个阶段完成后先验证，再进入下一阶段；耗时验证应停止并切换为更小的类型检查、DOM 度量或代表性截图。

### 当前视觉语法

| 语义 | 当前表达 | 使用边界 |
|---|---|---|
| 已有调用或数据流 | 蓝色实线 | 必须有代码、契约或实验支持 |
| 资源或基础设施边界 | 紫色 | 数据库、缓冲区、线程池等非业务参与者 |
| 成功结果 | 绿色 | 通过、完成、200 等成功结论 |
| 受控拒绝或暂停 | 橙色 | 401、403、背压暂停等预期控制结果 |
| 异常或阻断 | 红色 | 非预期错误、资源失败、流程无法继续 |
| 未测量或不在范围 | 灰色 / 虚线 | 不能从当前实验外推的部分 |

线型仍需遵守一个关键限制：虚线表示推断或未验证关系；异步边界必须另带文字标签，不能只靠虚线表达。

### 2.1 Node.js 运行时职责与反馈（P0）

认知问题：当前用户需要在多个专题和段落之间拼出“主线程、event loop、threadpool、OS I/O、流和进程”的职责边界。

最小改造：

- 建立统一 ownership map：主线程 / event loop、libuv threadpool、OS / kernel I/O、应用资源四个区域。
- 专题切换时复用同一组参与者，不为每个专题发明另一套颜色或箭头。
- event loop 用阶段环或有序轨道表达调度顺序，同时明确“阶段”不等于独立线程。
- threadpool 与网络 I/O 用分叉调用链表达，避免把所有异步工作都画进 threadpool。
- 背压用“生产者 → 缓冲区 → 消费者 → pause/resume 反馈”闭环表达。
- graceful shutdown 用“收到信号 → 停止接入 → 等待在途任务 → 清理资源 → 退出”的状态时间轴表达。
- 错误传播保留文字化边界，避免用一条红箭头把同步抛错、Promise rejection、Stream error 和进程事件压成同一种机制。

展示状态：默认给出职责全图，选中专题后突出相关参与者和边。

复习状态：先问“慢点属于哪一层、会阻塞谁、证据是什么”，回答展开后再显示 ownership 与未测量边界。

验收重点：用户不读完整段落，也能定位执行归属；但图不能暗示网络 I/O 一定使用 threadpool。

### 2.2 测试闭环与证据矩阵（P0）

认知问题：当前覆盖增量、两条认证流、fixture 和数据库生命周期已有内容，但它们之间的互补关系仍需要逐块阅读。

最小改造：

- 用覆盖拓扑表达“旧测试覆盖什么 → 缺口在哪里 → 新测试补到哪一层”。
- 用两条平行认证链对照 admin 登录后报表 200 与新注册 member 登录后报表 403。
- 用矩阵表达测试 / 观察结果 × 能证明 / 不能证明，至少保留：登录契约、JWT 使用、RBAC 分叉、报表 Controller 是否到达、真实 OAuth2 是否被覆盖。
- 用资源生命周期轴表达 fixture 创建、`JWT_SECRET` 设置、内存库连接、测试执行、清理和恢复。
- 状态码颜色服从统一语法：403 是受控拒绝，不使用异常红色。

展示状态：默认展示覆盖拓扑和两条链，证据矩阵可展开查看精度。

复习状态：先给测试名称与观察结果，要求判断能证明什么；提交或主动揭示后再显示矩阵答案。

验收重点：用户能直接回答“两个测试为什么不能互相替代”，且不会把 200/403 结果外推为数据库、OAuth2 或所有权限场景都正确。

### 2.3 数据库聚合形状与证据边界（P1）

认知问题：pipeline 顺序、每阶段数据形状、索引前后差异及事实 / 推断目前分散在卡片和文本中。

最小改造：

- 用 pipeline strip 表达 `$match → $group / $lookup → $unwind → $project / $sort` 等实际阶段。
- 每个阶段显示输入 / 输出形状的最小样本，只保留影响下一阶段的字段。
- 索引前后用 explain 指标的并排差异表，不把少量指标包装成柱图。
- 用“观察结果 → 能证明 → 不能证明”三列结构区分事实、推断和未测量项。
- `populate` 与 `$lookup` 只在需要解释调用次数或数据往返时使用调用拓扑；其余差异继续用文字表格。

展示状态：默认突出 pipeline 主链和形状变化，证据边界紧邻相关阶段。

复习状态：先隐藏阶段名称或输出形状，要求预测下一阶段结果，再逐步展开。

验收重点：图形不能把一次 explain 结果表达成普遍性能结论，也不能省略数据规模、过滤条件和索引前提。

### 3.1 手机端语义变体

手机端不要求机械缩小桌面图，而要保留相同结论：

- 时序 / 泳道：改成“当前消息 + 明确的起点 / 终点 + 可扫读步骤轨道”，避免四列压成不可读窄栏。
- ownership map：参与者变为稳定的区域标签，选中专题时只突出相关关系。
- 证据矩阵：按测试或观察结果逐行展开，重复显示列语义，避免用户横向记忆表头。
- pipeline：保持阶段顺序，允许局部横向滚动，但页面本身不能横向溢出。

### 3.2 展示 / 复习认知任务

### 审计确认仍然成立的部分

- `1440 × 1000` 与 `390 × 844` 共 11 个视图 / 状态，均无页面级横向溢出。手机端唯二超出视口的

- admin-only 选择器只占 `styles.css` 的 2.8%，**按板拆 CSS 没有收益，明确不做**。

### 本轮修复

1. 深色模式下 W3 → W4 → W5 → W6 的依赖箭头对比度只有 1.65:1（`--baseline` #383835 on #0d0d0d），
   实测几乎不可见。改用 `--text-muted`。
2. `role="tablist"` 原本是半实现：5 处 tablist，0 处 `tabpanel` / `aria-controls` / 方向键。
   展板主 tab、认证路径、W6 测试链补全为完整 tab 模式（`tabs.ts` 提供键盘契约）；
   登录/注册与图表/表格两处本就不是 tab，改为 `aria-pressed` 按钮组。
3. 手机端点击目标：`summary` 实测仅 14–17px 高（WCAG 2.2 SC 2.5.8 要求 24×24），统一抬到 32px。
   Markdown 正文里的行内链接属于「句子或文本块中的目标」，规范豁免，不为它撑高行距。
4. 手机端字号下限：小号文字统一走 `--fs-s1..s7` 梯子，桌面值不变，手机端整体抬高。
   连带修复背压 stage 在字号抬高后把整行顶出视口的问题（`1fr` 轨道改 `minmax(0, 1fr)`）。
5. `OAuth2FlowPanel` 从 `Dashboard.tsx` 抽到 `OAuth2Panel.tsx`，`Dashboard` 改懒加载。
   之前 Showcase 的一行 import 会把 `charts.tsx` / 报表视图一起拖进 SHOWCASE_ONLY 构建。
   入口 chunk 256.32 → 245.47 kB（gzip 91.27 → 87.92），charts 落到永不请求的 chunk。
   真正的收益是「展板无后端依赖」从 deploy skill 的 grep 约定变成结构约束。
6. 标题改由 `VITE_SHOWCASE_ONLY` 在构建期决定，并内联 favicon。
   deploy skill 里那条 `perl -0pi -e 's#<title>...'` 已经多余，可以删。

### 本轮已知残留

- 桌面认证 tab 比改动前矮 6px（2930 → 2924，0.2%），其余 10 个视图高度逐像素一致；

- 认证主链顶部四列 lanes 目前是装饰性的：消息行没有对齐到那四列，实际是列表而非泳道。

### A 档：W5 板内补齐（原本只有 4/5/6 有）

## 明确保留文字的页面与内容

- 前端笔记正文：Markdown 适合连续论述、代码、引用和可搜索的细节，图形化收益不足。
- 各实验的环境、样本量、命令和原始测量：图形不能替代可复核证据。
- 事实 / 推断 / 未测量的限定语：必须与图相邻保留，不能只藏在 tooltip。
- Node.js 错误传播的机制差异：适合短表格或文字边界，不应合并成一张看似统一的错误流。
- OAuth2 和认证的安全前提：图显示顺序，文字保留 `state`、凭据暴露面和“未接真实 provider”等限制。

## 依赖与风险

- 第二阶段依赖第一阶段 token 与状态语义保持稳定；若每页重新定义颜色，将失去跨页一致性。

- 过早抽象共享组件可能增加维护成本；只有相同结构在两个以上页面稳定复用后才提取。
- 当前三个阶段改动仍在工作区中；新对话开始时必须先读 `git status --short`，不得覆盖或回退这些改动。
