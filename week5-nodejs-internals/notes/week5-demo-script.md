## 0:50–3:40 · 第一段：工作由谁推进

### 页面操作

1. 先指任务归属表。
2. 再指普通网络 I/O 的职责链。
3. 播放 `SIZE=4`，然后切换到 `SIZE=8`。
4. 最后停在三类慢诊断表和「运行时判断」。

### 讲稿

> “看到一个异步 API，不能直接得出‘它在后台线程执行’。同步 JavaScript 由 V8 在主线程执行；异步 `pbkdf2`、部分 `fs`、`zlib`、`dns.lookup`，以及当前项目的异步 bcrypt 会使用 libuv threadpool；普通 HTTP 或 MongoDB 网络等待，主要由操作系统非阻塞 I/O 和 libuv poll 推进。”

指向网络 I/O 职责链：

> “这里还要区分代码调用顺序和职责归属。JavaScript 发起 Node API；操作系统维护 socket 和就绪状态；libuv 监听 I/O 事件；Node 处理协议和对象语义；最终 callback 仍然回到 JavaScript 主线程执行。底层工作完成，不等于 callback 已经执行。”

播放两组 `pbkdf2` 数据：

> “我连续提交了 8 个参数相同的 `pbkdf2`。`UV_THREADPOOL_SIZE=4` 时，callback elapsed 出现约 4 加 4 两批，总时间 151ms；改成 8 时，8 个 callback 聚成一批，总时间 119ms。”
>
> “事实是完成分组发生了变化。结合 `pbkdf2` 的执行归属和受控变量，可以推断前一组存在 worker 排队。但 elapsed 混合了排队、计算和 callback 调度，不能把它说成精确排队时间。”

落结论：

> “所以调大 pool size 只可能改变使用 threadpool 的任务排队，不会让 JavaScript 主线程变成多线程，也不会加速普通网络 I/O。worker 增多后 CPU 核心数没有增加，因此它不是万能性能开关。”

转场：

> “第一段解决的是工作在哪里。第二段换一个问题：主线程没有被卡住，但上游持续比下游快，内存仍然可能积压。”

点击「背压：让快生产者停下来」。

## 3:40–6:50 · 第二段：谁应该暂停

### 页面操作

1. 指向实验配置：`10ms / chunk`、`50ms / chunk`、`highWaterMark = 5 bytes`、总量 30。
2. 点击重放；必要时暂停并单步走一轮 `false → 停产 → drain → 恢复`。
3. 指向 30 / 6 / 5 / `1 → 5 → 0` 四个结果。
4. 最后指向「终止边界」和「运行时判断」。

### 讲稿

> “这个实验故意让 producer 每 10ms 产生一个 chunk，而 consumer 每 50ms 才完成一个，所以下游持续更慢。这里的风险不是同步 CPU 阻塞，而是未完成数据越积越多。”

随着动画讲控制链：

```text
write() 返回 false
→ producer 停止后续写入
→ consumer 与 heartbeat 继续
→ drain 后 producer 恢复
```

> “`write()` 返回 `false` 不代表当前 chunk 写入失败。当前 chunk 已经被 Writable 接纳，`false` 是对后续生产的反馈：先暂停，等 `drain` 再继续。”
>
> “暂停窗口里 consumer 和 heartbeat 都还在继续，这也是重要证据：这里发生的是流速协调，不是整个 event loop 被同步代码卡住。”

指向结果：

> “本次 30 次 write 中有 6 次 false、5 次 drain，`writableLength` 每轮重复 `1 → 5 → 0`，峰值没有持续抬升。最后一次 false 后已经没有下一块数据，所以 producer 直接 `end()`，剩余数据处理完后由 `finish` 收口，不需要第 6 次 drain。”

落结论：

> “`highWaterMark` 是触发背压的阈值，不是永远不能超过的硬内存上限；`drain` 只说明本地 Writable 可以继续接收，也不代表远端客户端已经收到。实际 review 手写写入循环时，我会检查 false 到 drain 之间上游是否真的停产。”

转场：

> “背压说明正常流动时怎样协调速度。最后再看异常和退出：不同类型的结束，不能都交给同一个全局 catch。”

点击「错误边界与进程收口」。

## 6:50–9:20 · 第三段：谁负责收口

### 页面操作

1. 先按从上到下的顺序指三行接管边界：请求级、进程级 fatal、计划内信号。
2. 再指向 single-flight graceful shutdown 六步流程。
3. 最后指向 Fatal 边界。

### 讲稿

> “判断一个错误由谁处理，先看它是否还连接在原来的请求链上。同步 handler 的 throw、返回或 await 的 rejected Promise，以及 await `pipeline()` 的失败，都还能交给 Express error handler；响应仍可发送时，它们可以翻译成 HTTP 错误，进程继续运行。”
>
> “悬空 Promise、detached timer 里的 throw、未监听的 EventEmitter `error` 已经逃出请求边界，会进入 `unhandledRejection` 或 `uncaughtException`。这时进程状态可能已经不可信，进程级监听器只做最小诊断并异常退出，不应该吞错后继续运行。”
>
> “`SIGINT` 和 `SIGTERM` 又不同。它们是计划内终止信号，应该进入 graceful shutdown，而不是当成 fatal 异常。”

沿六步流程讲：

> “第一次信号先锁定 single-flight，重复信号明确忽略；30 秒 deadline 从收到信号一直覆盖到数据库断开；如果服务仍在启动，要先协调启动状态，保证关停后不会再次 listen；然后 HTTP 停止接收新请求并排空已有连接，最后断开数据库。成功设置 `exitCode = 0` 自然退出，失败或超时用退出码 1。”

补真实修复：

> “原服务快速连续按三次 `Ctrl-C` 会重复执行 MongoDB 断开。加上防重入和唯一关停链后，shutdown 只执行一次。这里解决的不只是退出顺序，还包括启动期竞争、重复信号和端到端超时。”

边界一句：

> “应用内 deadline 也依赖事件循环。如果主线程被同步代码永久阻塞，它不能提供最终强杀，所以生产环境仍需要容器或 supervisor 兜底。”

## 现场追问锚点

### 为什么不直接把 `UV_THREADPOOL_SIZE` 调大？

它只影响使用 libuv threadpool 的部分 API；worker 增加不等于 CPU 算力增加，还可能带来 CPU 竞争和调度成本。先确认任务归属，再用受控实验验证。

### `write() === false` 是不是写失败？

不是。当前 chunk 已接纳；`false` 要求 producer 暂停后续写入，等待 `drain` 再恢复。

### 为什么 fatal 错误不走完整 graceful shutdown？

fatal 错误表示进程状态可能已经不可信，不适合继续执行复杂异步收尾。计划内信号才走完整 shutdown；最终重启和强杀由外部 supervisor 负责。
