### 0.3 D2 带来的三样东西（初稿里没有）

1. **一整块新内容：机制层的失效。**
   十四条计划外事件里，**没有一条是流水线逻辑错**——Checkout / Install / Test 的阶段划分一次就对。
   成本全花在**构建环境与工具行为**上：launchd 的 PATH 不是登录 shell 的 PATH、

   可迁移的一句：**把一段手工操作交给机器，改写的不是逻辑，是环境假设。**

2. **W10 那句「自动检查全绿 ≠ 语义生效」第一次在本周有了实测样本，而且是自己设的验证抓到的。**
   验证 ②a：env 文件建了、路径也已按实测修正、`brew services list` 显示 started、RSS 282 MB 还在 720M 止步线以内——
   **四样都对，唯独 `JAVA_TOOL_OPTIONS` 根本没被 JVM 读到**（jcmd 实测 MaxHeapSize = 8 GiB，不是 512 MiB）。
   它被抓到的唯一原因，是开工前 review 补了 ②a 这一项（F3 的原话：② 只量 RSS，**对 P2 是否生效不敏感**）。
   **一条对它要验的东西不敏感的验证，就是一格假绿。** 这句比 D1 那六条更硬，因为它有命令输出可查。

3. **一个新的盲区，而且 D3 要依赖它。**
   轮询遇网络失败被静默记成 `No changes`——**不触发，也不报错**。人看到的是「流水线没动静」，
   而「没动静」有两种含义。这与 W10 ⑦「没红过的检查区分不了『一切正常』和『检查根本没在跑』」是同一族，
   换了个宿主又长了一次。

## 1. 这份方案要解决的问题

D1 产出的是一份 760 行、18 条决策、五张表的契约，D2 又在它后面接上了一份九步执行记录。
两份都自洽、可执行，但有四个缺口是文字形态天然填不上的（第 4 条为 D2 收口后新增）：

1. **「谁在哪一侧执行」与「失败了会怎样」是同一条线，而契约把它们拆在两张表里。**
   契约 §5.1 的第 2 列（在哪一侧）与第 5 列（失败时服务器处于什么状态）读起来是两件事；
   实际上前三阶段之所以零影响，正是因为它们**不在服务器那一侧**。这条对应关系是本周最核心的心智，
   现在要读者自己在两列之间连线。

2. **契约里最贵的三条，是「两条各自合理的条款合起来是错的」——而它们散在四个地方。**
   B1（controller 侧 `npm ci --omit=dev` 会砍掉 jest）、B2（`logger` 谁都能打，标记不能承担信任）、
   B3（nodeapp 是 nologin，SSH 唯一入口是 ubuntu），加上 wrapper 位置参数被 `command=` 吞掉、
   openjdk 17→21 的事实修正，分别落在 Q4 / Q9 / Q14 的答案里、契约 §4.1 的自查行里、
   `day1-contract-freeze.md` §3 的偏差表里、`day2-controller-setup.md` §2.1 的修正注里。
   **它们是同一族的**：纸面推演抓到的、机器抓不到的、换任何一套 CI 工具都还会再犯一次的。

3. **本周有一批「已经决定、但还没有对象」的格子，文字写不出它们离真实还差多远。**
   越权验证的两条输出、bcrypt 在服务器侧走预编译还是走编译、`systemctl restart` 的实际不可用时长、
   回滚三条路径里哪一条真的走过——全是 D3 / D4 才有的。**这正是 `contract` 档位存在的理由**，
   而板头计数会把「这块板哪一半还是一张纸」这件事诚实地写在最上面。

4. **D2 的十四条计划外事件挤在一张收口核对表里，而其中三条是判据级的。**（2026-08-25 新增）
   多数条目是「遇到了、修了、记下来」；但 ②a（**验证对它要验的东西不敏感**）、
   轮询静默（**失败被记成无变化**）、`CI=true`（**预测的前提当场不成立**）这三条，
   换任何一套 CI 工具都会再遇到一次。表格把三条判据和十一条排障编在同一个序列里，
   读者拿不到「哪几条值得记住」——这恰好是版面能做、文字做不了的分层。

本方案不发明新语法，只做一处扩展（§3.2 的「两侧」空间约定），骨架仍是 **契约 → 实测 → 差在哪**。

### 3.2 唯一的新增：贯穿全板的「两侧」空间约定

## 5. 板块设计（八块，每块只回答一个问题）

> 2026-08-25：⑥ 由一块拆成 ⑥·1 / ⑥·2 两块，全板七块变八块（理由见 §0.4 第 1 条）。

> 每块后面标了**最早开工日**——这是本方案里最实质的一列，理由见 §10。

### ① 三条自动化，一把钥匙（`topic=lanes`）· 最早 D5

**空间编码**：从一次 `git push` 出发的三条并排轨道——GitHub Actions / Jenkins / W9 手工发布——
各自止步在不同位置；右侧服务器画成一个**只有一个入口**的盒子，只有 Jenkins 那条轨道上挂着钥匙并接进去。

**一眼结论**：三条自动化跑着同一份测试，**能写服务器的只有一条**。
Actions 红了不影响部署，这是拍板过的决策（Q3），不是漏配——写在轨道终点旁边，
否则第一次出现「Actions 红但部署绿」时会被当成 bug。

**第二条结论（轮询那一段）**：整条链只有这一段不是事件驱动的，画成一段带刻度的等待段（上限 5 分钟）。
webhook 走不通是**网络位置**决定的，不是配置——这一句紧贴着画。

**轮询还有第三条结论，但不在这块画**：失败被静默记成 `No changes`（D2 实测）——
它属于「工具行为与预期不符」，归 ⑥·2；这里只在等待段旁挂一句指针。
同一结论不讲两遍（核查线三问第 2 问）。

**为什么排最后**：三条轨道里 Jenkins 那条的终点位置在 D2（止于 Test）与 D3（延伸到 Deploy / Verify）**各不相同**；
而且 D2 期间它轮询的是**功能分支**不是 main（P3+P4 的临时偏差，D3 改回 `*/main` 即消除）。
D5 之前画哪一版都会当天过时。

### ② 五阶段：哪一阶段能把服务器弄坏（`topic=stages`）· 最早 D2 收口后 —— 建议第一批

**空间编码**：五阶段横排在「两侧」约定上（前三阶段整段在左半，第 4 阶段跨中线，第 5 阶段发起在左、目标在右）；
每阶段下面一条「服务器状态」轨道。

**一眼结论**：五个阶段里**只有一格是「可能中间态」**，而它恰好是唯一跨过中线的那一阶——
**在哪一侧执行，和能造成什么后果，是同一条线**。前三阶段的服务器状态是一整段连续的「未被碰过」，
不是三段各自写「未动」。

**第二条结论（失败后的动作有三种，不是一种）**：人工介入（阶段 1–3）/ 自动回滚（阶段 4）/
**已部署且不自动回滚，人工判定**（阶段 5）。第三种最容易被读错——画成一个停在服务器侧、等人来按的终点。

**D2 补进来的一格（初稿没有）**：前三阶段的「未被碰过」现在**不是设计推论，是被证明的**——
装 Jenkins 前后各采一次服务器七项只读基线（认证 / 特权 / 监听 / 服务 / 工作副本 / 进程 / 临时文件），
diff 的唯一差异是 nodeapp 进程的 RSS 与累计 CPU 两个动态列。**「零改动」因此是一条有对照组的结论。**
紧邻要写的一句：那次对照也暴露了方法自身的粒度问题——全量 `ps aux` diff 会引入动态噪音，
进程项应只比 PID 与 COMMAND 是否新增或消失。**对照基线选错粒度，会把噪音读成变更。**

**档位（D2 收口后）**：阶段 1–3 是 `measured`——Install 514 包 24 秒、Test 3 suites / 9 tests 12.9 秒、
一次由 `Started by an SCM change` 自动触发的绿构建、一次变红实验与还原；
阶段 4–5 仍是 `contract`，每一格必须写清**证据差在哪**（沿用 W10 的 `caveat` 纪律，档位标签一个词带不过去）。

**两条必须紧邻的 caveat（D2 产生，不写会让「测试绿」被读成「生产没问题」）**：

- Test 阶段的库来源是 **MMS（mongod 8.2.6）**，Actions 是 **mongo:7** 容器，生产是另一个版本——
  **三源全不同**。所以这一阶段的绿证明的是**隔离环境里的行为**，兜底在 D3 的 Verify（真实 mongod + 只读探活）；
  低频路径（报表聚合 / 权限校验）上的版本差异，Verify 也探不到。
- 为了让这一阶段跑得起来，本周改了**被测项目**的 `package.json`（jest 串行 + 超时 30 秒）——
  这是本周第一次为流水线改被测项目的配置。属边界内（不是业务逻辑），但要在格子里留痕。

### ③ 部署身份的权限收窄：从全权免密到两层限制（`topic=trust`）· 最早 D3 收口后

**空间编码**：一个身份 `ubuntu`，两条并排通道（个人密钥 / 部署密钥），每条通道上串两层限制
（`authorized_keys` 的 `command=` 与 `sudoers` 白名单），每层下面写它拦住哪一类命令。
左右两半是前后对照：**现状**（8/24 实测 `sudo -l`：四行全权免密）→ **收窄后**（两行四条白名单 + 三条 wrapper 命令）。

**一眼结论**：两层限制的作用域不同。`command=` 限制的是这把密钥登录后能执行什么，
`sudoers` 限制的是这个用户能提权执行什么。只配置其中一层各自会漏哪一类命令，用两条穿过两层的轨迹表示。

**必须紧邻的一条（F1 的代价）**：收窄的不是部署密钥，是**整个 ubuntu 身份**——
个人密钥登录后的手工运维（`journalctl` / `nginx -t` / `tail`）也会一起被挡住，要用先加白名单。
这一条不写在图旁边，D3 当天第一次被拒时会被当成配置错误去「修」。

**档位**：现状那半是 `measured`（块 C 实测）；收窄后那半到 D3 越权验证的两条输出落地才翻档。
**在此之前，这块板上「被拒」的那两个格子是空的**——空格本身就是「还没验证过」的形态，不补。

### ④ 回滚：三条路径，两个指针（`topic=rollback`）· 最早 D4 收口后

**空间编码**：一条提交时间线上放两个指针——`.rollback_target`（本轮部署开始时的快照）与
`.previous_commit`（最近一次验证通过的版本）；三种失败发生在链路的不同位置，箭头各自回到不同的指针；
第三条路径（回滚动作本身失败）**没有目标**，画成断在半空的箭头。

**一眼结论**：**正常时两个指针指着同一处，所以最容易被合成一个文件——而它们分开的那一刻，正是需要回滚的那一刻。**

**第二条结论**：回滚不是切一个指针，是**重跑一次旧版本的完整部署**（`git reset` + `npm ci` + restart）——
因为形态选的是原地更新。「逻辑原子性」不等于原子切换，这两个词的差别就是这块图与一张 symlink 切换图的差别。

**必须紧邻的一条**：首次基线 `.previous_commit = 6a1b1a1` 是**未经部署后验证的 commit**（W10 收口态没有这一步），
它只是「当前唯一已知可用态」。这个限定语一旦被抹掉，回滚看起来就是闭环的。

**为什么排到 D4 之后**：三条路径在 D4 之前只有一条会被真的走过；三条画得一样粗，就是把两条预测画成了实测。

### ⑤ 部署后验证：七项各自证明不了什么（`topic=verify`）· 最早 D3 收口后 —— 与 ⑥ 并列的代表页

**空间编码**：七项验证 × 五层覆盖（进程存活 / socket 绑定 / HTTP 路由 / DB 可连 / 对外反代语义）的矩阵，
最右一列是每项**「它证明不了什么」**——这一列是本块的重心，不是备注。

**一眼结论**：**没有任何一项能单独证明一次部署成功**；`/health` 只覆盖一层，
而覆盖「对外反代语义」那一层的**只有一项**（公网 curl）——那一格只有一个点，删掉它整层就空了。
这正是 W10 盲区②在本周被补上的方式。

**第二条结论（仍有覆盖不到的）**：`/admin/` 静态面没有任何一项验证碰得到（Q15 明写）；
「进程活着但没绑定」只有 `ss` 那一项兜得住，而它的根因到 D4 才复现——**那一格标 `pending`，不标绿**。

**必须紧邻的一条（两个口径并存）**：常驻检查不上公网探针（W10 结论，理由是不依赖外部路径），
部署后验证可以（一次性、有人在场）。两句写成并列的一对，**不是后者推翻前者**。

**为什么它可迁移**：换掉 Jenkins、换掉 Node，这张表的形状不变——**每加一项检查，都要同时写下它证明不了什么**。

### ⑥·1 契约层：纸面推演抓到的六条（`topic=selfcheck-contract`）· **现在就完整** —— 代表页，建议先做

D1 换来的：**一份契约里，两条各自合理的条款合起来可以是错的；
而这一层没有任何机器工具，只有纸面自查。**

**空间编码**：纠错三段式（❌ 原以为 → ⚡ 实际机制 → ✅ 修正），六行；最右一列**「谁抓到的」**。

| # | 原以为 | 实际机制 | 谁抓到的 |
|---|---|---|---|
| B1 | `npm ci --omit=dev` 装一次就够 | controller 侧要跑测试，jest / supertest / MMS 都在 devDependencies | 冲突自查（Q5 × Q6） |
| B1' | Verify 通过后回滚基线自然会更新 | 没有任何通道写 `.previous_commit`——wrapper 白名单里必须补第三条命令 | 冲突自查（Q12 × Q9） |
| B2 | `logger -t DEPLOY` 的标记只有 wrapper 能打 | `logger` 任何登录用户都能写，`/dev/log` 普通用户可写 | 安全论证复核（Q14） |
| B3 | 用 `nodeapp` 身份 SSH 上去部署 | nodeapp 是 nologin，SSH 唯一入口是 ubuntu；仓库属主又是 nodeapp | 事实核对（块 C `id nodeapp`） |
| — | wrapper 接客户端传来的位置参数 | `command=` 会吞掉客户端命令，必须读 `SSH_ORIGINAL_COMMAND` | 机制核对（Q9） |
| — | 先装 `openjdk@17` 再装 Jenkins | formula `depends_on "openjdk@21"`，service 硬编码走 21 的路径 | 读 formula 源码（D2 起草时） |

**一眼结论（由「谁抓到的」那一列承载）**：**六条里没有一条是机器抓到的**——全部来自冲突自查、事实核对与读源码。
把它和 W10 ⑥ 并排：那边是「三项自动检查全绿，四条缺陷仍穿过去，只有一条被自动手段挡下」；
这边是「零条」。这一层**根本还没有机器可用**——契约在那一刻还不是任何工具的输入。

**B2 换一套工具仍然成立**：任何登录用户都能写入的标记，不能作为抑制告警的凭据。
修法也要画出来——不是给标记加权限（`logger` 加不了），是**改成交叉验证**（系统日志里的 commit + BUILD_NUMBER
要与 Jenkins 当次构建记录对得上，且未超时）。

**与 ⑥·2 的边界**：这一页讲**动手之前**（判断力来自纸面推演），下一页讲**动手之后**（判断力来自一条命令的输出）。

### ⑥·2 机制层：D2 十四条计划外事件里判据级的三条（`topic=selfcheck-runtime`）· **现在就完整** —— 2026-08-25 新增

D2 换来的，也是 W10 ⑥ 那句话在本周的第一个**实测**样本：
**服务起来了 ≠ 参数生效了；轮询安静 ≠ 没有新提交。**

**空间编码**：与 ⑥·1 同一套纠错三段式，但最右一列换成**「抓到它的那条命令」**——
两页并排看，⑥·1 那一列全是纸面推演，⑥·2 这一列全是一条可以当场重跑的命令。

| # | 原以为 | 实际机制 | 抓到它的那条命令 |
|---|---|---|---|
| ②a | 服务 started + RSS 在止步线内 = 堆参数生效了 | brew 6.0.6 的 plist 里没有 `EnvironmentVariables`，`etc/services/*.env` 压根不被读；**MaxHeapSize 仍是默认 8 GiB**，不是合约里的 512 MiB | `jcmd` 读实际堆参数（开工前 review 补的验证 ②a） |
| CI | 构建环境不会有 `CI` 这个变量，所以测试会走 MMS | Jenkins 2.568.2 **内置注入 `CI=true`**（与 Actions 同行为，不来自任何可配置位置）——P6「CI 未注入」的前提当场不成立，测试会直接抛「CI 环境必须给 `MONGODB_URI`」 | 一分钟的冒烟构建里的 `printenv CI` |
| 轮询 | 轮询失败会报错，看得见 | 网络失败被记成 **`No changes`**，既不触发也不报错；「流水线没动静」有两种含义 | 翻 `scm-polling.log` |

**另外两条不判据级、但成本最高，同一形态**（放在同一页的下半，不单独占页）：
`node: command not found`——launchd 拉起的构建环境 PATH 不是登录 shell 的 PATH，
块 C 采到的 v24.18.0 是 nvm 的值，构建实际用的是 `/usr/local/bin` 的 v24.16.0（**一台机器上有四个 node**）；
MMS 的**两级缓存**（项目级 vs 用户级）加 jest 默认并发两个 worker，双因素叠出 `beforeAll` 超时，
根因靠一次串行实证才分开。

**一眼结论**：**十四条里没有一条是流水线逻辑错。** 用一条竖直分界画出来——
左栏「阶段划分 / 流水线逻辑」**整栏是空的**，右栏「构建环境与工具行为」堆满。
空栏本身就是结论：**把一段手工操作交给机器，改写的不是逻辑，是环境假设。**

**第二条结论**：这三条都要一条命令的输出才能确认。②a 被发现的原因是开工前 review 追问了一句：
那条验证对它要验证的对象是否敏感。
**一条不敏感的验证等于一格假绿**——它和 W10 ⑥ 的四条实例同族，但这次有 `jcmd` 的输出可查。

**与 ⑤ 的边界**：⑤ 讲「每一项检查证明不了什么」，⑥ 两页讲「**检查本身可能是假的**」——
⑥·1 是契约条款之间的不一致，⑥·2 是检查通过但语义未生效。

### ⑦ 与手工部署的对照：哪几步没被替掉（`topic=handoff`）· 最早 D5

**空间编码**：W9 手工发布的六步 × 三种归属——**被流水线替掉 / 仍需人执行 / 本周明确不交给自动化**。

**一眼结论**：替掉的只是中间那几步；两端各留着一批。而**两种「没被替掉」必须是两种画法**：
- `nginx -t && reload`、证书、ufw 是**主动不交**（W9 的收口成果，本周边界，将来可以改）；
- 「验证不绿要不要回滚」是**不能交**（Q12：验证失败不自动回滚，人来判定）——它不是本周的额度问题。

把这两种画成同一种颜色，交付成果⑤ 就答错了一半。

**第三格（controller 在开发机的代价）**：关机 / 休眠即流水线不存在——这条按 Q1/Q2 显式接受过，
它属于「没被替掉」的第三类：**替掉了，但依赖一台会关机的机器**。

### 明确不单独成块

- **九对冲突自查**：挂到对应格子上（例如「两侧依赖集合不同是设计」同时出现在 ② 与 ⑥·1），板头只留一行「九对全过」状态。

## 8. 口径边界总表（本次最容易做错的十一处）

> 第 9–11 条为 2026-08-25 D2 收口后新增。

| # | 边界 | 做错会变成什么 |
|---|---|---|
| 1 | **部署段的格子（阶段 4–5、③④⑤ 三块）在 D3 之前仍是 `contract`** | 把一份纸面契约画成一条在跑的流水线——本板最大的过时风险。D2 之后前三阶段已翻档，**更要分清哪一半翻了** |

### 14.3 执行期修的四处

**1. 方案里那条「临时偏差带失效日期」的断言，本批无对象。**

**2. 五阶段那条轴原本把中线画在第 4 格**左边**。**
那样画出来的是「第 4 格在服务器一侧」，而它实际是「发起在 controller、落点在服务器」的一段。

**3. 纠错卡左侧的徽标被 grid 拉伸成一根竖条。**
`place-items: center` 在会拉伸的单元格里等于让徽标占满整张卡的高度，机制层那两个词
（判据级 / 代价最高）还被折成两行。改成 `align-self: start` 并给它一列放得下的宽度。

**七项里没有任何一项走过应用自己的数据库连接**（本地健康端点与本地业务接口的代码都不查询数据库，可在仓库中核对）。

**3. ③ 的逐条说明与 ⑤ 的逐项说明首版是常驻列表，两页因此偏高（2.77 屏与 2.30 屏）。**
两页各收进一个折叠区后降到 2.32 屏与 1.96 屏。⑤ 那份列表与矩阵最后一列讲的是同一件事，
折叠之后矩阵承担结论、列表承担细节，读者不必读两遍。

**4. ⑥·3 的列脚要两行才读得出来。**
只有「冻结时的依据合计」一行时，最右列的合计是 0，而那一列里看得见 4 个实心标记，图与数字互相矛盾。
补第二行「实测之后的依据合计」，两行分别对应空心与实心两种标记。

**5. 反向证明当场暴露了断言自身的一个缺陷。**
第一版的两条断言用 `innerText()` 直接读那一格，格子消失时抛超时异常、整个脚本崩掉，
失败清单一条都打不出来。改成先数再读，读不到时如实记为该格不存在。
**一条在结论被推翻时崩溃的断言，和一条不会红的断言，对使用者是同一件事。**
