## 2. 估算偏差一：按箭头数估，按接触面数付

**原判断**：方案是四个箭头（手机 → GitHub → Jenkins → 服务器），实现量不大。

**实际现象**：信息流从起草到跑通一次没改过，但变更单 §9.2 记下 A–K 共 11 条执行期偏差，其中零条落在流水线的阶段划分上。

**关键证据**：11 条偏差分别落在 Jenkins 插件管理（A）、Yarn 与 `.gitignore` 的交互（B）、Groovy command expression 解析（C）、Groovy 字符串转义层级（D）、workspace 文件跨构建残留（E）、`git push --dry-run` 的协议行为（F）、GitHub deploy key 与分支保护的优先级（G、H）、vite 输出的 ANSI 控制字符（I）、git plugin 的轮询扩展弃用（J、K）。

**偏差类型**：估算模型错误，不是执行不力。方案的复杂度由箭头数决定，工作量由**接触面数**决定——本链路实际要动 7 个系统：Jenkins 插件、Groovy 脚本沙箱、git plugin 扩展、GitHub deploy key、GitHub 分支保护、服务器 `authorized_keys`、macOS 电源管理。每个系统的默认行为只在真跑时暴露。

**修正**：首次打通一条新链路，按「接触面数 × 45 分钟」估。本链路 7 个接触面 ≈ 5 小时，与实测 4 小时 55 分吻合。

**边界**：该系数来自单次样本，尚未在第二条链路上复验。

## 3. 估算偏差二：验证是主体工作量，但没有进预算

**原判断**：变更单的 9 条可证伪验证是实现完成后的确认动作。

**实际现象**：pipeline 首版编写耗时远小于验证耗时；9 条验证中有 2 条的第一版判据测不出它要测的命题，同一形态在当晚重设判据时第三次出现。

**关键证据**：

| 条目 | 目标命题 | 首版判据为什么测不出 | 暴露方式 |
|---|---|---|---|
| §9.2-F | main 上有分支保护 | `git push --dry-run` 只协商不发送数据，不触发 GitHub pre-receive 检查。本地与远端一致时无论有无保护都输出 `Everything up-to-date` | 改真实 push（空提交）后才有区分 |
| §9.2-J → K | 回执 push 不触发新构建 | 「10 分钟无新构建」在「过滤生效」与「轮询未运行」两种情况下取值相同 | 手机侧真实触发后 45 分钟零构建 |
| 陷阱 1 重验（2026-08-26 当晚） | 回执 push 只引出一次 `NOT_BUILT` | 「receipts 无新增」在「起了一次 `NOT_BUILT`」与「一次构建都没起」两种情况下取值相同——`NOT_BUILT` 分支本就不写回执 | 设判据时当场识别，改为查 Jenkins 构建列表 |

**共同形态**：判据在「机制正确」与「机制未运行」两种情况下取值相同，因此不承载信息。

**须与判据失效区分**：§9.2-G（main 无保护、write 权限 deploy key 输出 `Bypassed rule violations` 绕过规则）不是判据缺陷，而是 F 的判据修正之后**暴露出来的真实缺陷**。判据在这里是有效的，它正确地报了红。

**偏差类型**：预算遗漏 + 判据设计缺陷。

**修正**：见 §5 第 1 条。

## 4. 返工的三种性质

11 条偏差按性质分三类，处理方式不同。

| 类别 | 条目 | 说明 |
|---|---|---|
| **推翻了会长期误导的结论** | `252b5db`、`e72aadd`、§9.2-G、§9.2-K | 不返工的代价是留下一条「记录为已验证、实际不可用」的链路。K 条尤其明确：验证 6 当时记为 ✅，而真实状态是轮询未运行。G 条是 F 的判据修正后暴露的真实缺陷，不属判据失效 |
| **首次集成的实价** | §9.2-A、B、C、D、E、I | 工具默认行为与本项目组合方式的首次相遇，无法靠更仔细的设计提前消除 |
| **判断失误** | §9.2-J 的处理、`19cbe09` 前的脚本第一版 | J 条当天已记下 `The extension that requires a workspace for polling is deprecated`，处理写的是「观察，若后续自触发再改」，只设了假阳性一侧的观察判据 |

第三类可追溯的代价约 1 小时（15:00 触发写入到 16:16 发布成功）。

## 5. 两条写进变更单模板的修正

### 5.1 可证伪验证必须双向

一条验证若只写「某现象不出现」，它同时兼容「机制正确抑制了该现象」与「机制根本没运行」。这类判据不算通过。

以陷阱 1 为例，正确形态是两句成对：

1. 一次 `trigger.json` 改动**能**在 ≤5 分钟内起构建；
2. 一次回执 push **不**起新构建（起一次 `NOT_BUILT` 且不写回执，属于预期内）。

缺第 1 句时第 2 句不承载信息。

### 5.2 构建日志里的弃用警告不能用「观察」结案

处理方式二选一：当场设一个**会失败**的判据并执行，或记入 `DEBT.md`。写「若后续出现 X 再改」等于把判据推迟到某个特定失败模式上，其他失败模式不在观察范围内。
