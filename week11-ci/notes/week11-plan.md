## 2. 计划分析

### 2.1 合理之处

1. **部署目标沿用 W9 服务器，题面收在「自动化」这一层。** 拓扑不变，本周新增的只有产物流水线这一条正交线（W9 D4 §10.3 已给出这两层的划分），学习注意力不会被重新搭环境消耗掉。
2. **前置资产齐备，且是真资产。** 测试（jest + supertest + mongodb-memory-server）、部署链路（git clone + systemd + Nginx）、部署后验证（五面 curl + 四项检查）三样都已存在并被实测过，本周是把它们串起来，不是从零造材料。
3. **交付成果②「与手工部署的对照说明」是可证伪的终点。** 它要求回答的问题是「哪几步被替掉了、哪几步没有」，比「装了 Jenkins」更能证伪，也正好承接 W9 那句「今天手工做的每步都是脚本要复刻的真相源」。
4. **凭据管理与回滚策略是当前能力画像里的空白项。** W9 的结论是「仓库公开，零凭据上服务器」，那是刻意回避凭据问题的合理选择；本周把它正面解决一次，且是在只有一台机器、后果可控的规模上解决。

### 2.2 与本仓库现状冲突、需要在 D1 拍板的九处

> 下面九条是**问题**，不是答案。逐条的结论由本人在 D1 冻结（§5）。

1. **「代码推送后自动构建」与「controller 在开发机」这两条在同一句里成立不了。**
   GitHub 的 push 事件要送到 Jenkins，需要一个**公网可达的 HTTP 入口**；开发机（macOS，见 W9 / W10 笔记多处记录）在 NAT 后面，没有这样的入口。
   候选出路各有代价：SCM 轮询（能自动，但不是事件驱动，有轮询间隔的延迟，且会持续拉远端）；把 controller 放到那台 2 GB 服务器（超出内存上限，且与表内「不与部署目标同机」的前提冲突）；用隧道把 webhook 引到开发机（等于新开一个公网入口，扩大 W9 的信任边界）；降级为手工触发（可控，但验收成果①里的「自动」要重写）。
   **这一条决定验收句本身**，必须第一个拍。

2. **开发机关机时流水线不存在。** controller 跑在个人电脑上，意味着可用性依赖这台电脑是否开着、是否休眠。这在本轮学习目标下可能是可接受的代价，但**必须显式接受**，并决定 demo 时怎么演示（现场触发一次，还是放录制好的构建记录）。

3. **仓库里已经有一条在跑的 CI。** `.github/workflows/ci.yml` 已经在每次 push 时跑测试与前端构建。Jenkins 加进来之后，两条流水线跑的是同一份测试，需要定义关系：并存（Actions 覆盖仓库侧的测试，Jenkins 覆盖发布侧的验证）还是替代；两边结论不一致时以哪个为准。不定义的后果是出现两个口径不同的通过结论。

4. **「环境分离」在单机上没有对应物。** 这与 W10「集中收集」在单机上没有对应物是同一种问题：词面来自多环境场景，而这里只有一台机、一个 MongoDB、一个 systemd 单元。
   可选的落法：只做**凭据与配置的分离**（`.env` 不入库、由 Jenkins credentials 注入，不建第二套环境）；在同机开第二个端口 + 第二个库名的 staging 单元（占用内存，且多一个需要维护的公网面）；staging 放本地 Docker。
   **需拍板本周把「环境分离」定义成什么、止步在哪。**

5. **让自动化能部署，就必须在服务器上开一条可写通道，而 W9 的结论是「零凭据」。**
   要定的是一整套而不是一个开关：用哪个用户、怎么认证、密钥落在哪、这个身份能执行哪些命令、能不能免密 `sudo systemctl restart nodeapp`、密钥泄露时的止损动作是什么。
   这是本周最大的一处**信任边界变更**，按 W9 的纪律它属于「先冻结再动手」。

6. **测试跑在哪一侧，牵涉的是内存而不是习惯。** `mongodb-memory-server` 会下载并拉起一个真实 mongod 进程；在 available 1388 MB、swap = 0 且已经跑着 mongod + Node + Nginx 的机器上再拉起一个，属于 W10 已经暴露过的那类反模式。
   **需拍板**：构建与测试是否只在 controller 侧发生，服务器只接收一个「已经通过验收的 commit 或产物」。

7. **「部署」到底部署什么，决定了回滚形态和 S3 有没有归档对象。**
   当前形态是服务器 `git clone` 整仓，部署等于 `fetch + checkout <commit> + npm ci + restart`。
   若维持这个形态：服务器每次部署都要联网装依赖，`bcrypt` 的原生依赖是否需要编译工具链要先确认，且**依赖装到一半失败时服务处于什么状态**没有定义。
   若改成打包产物：Node 应用没有编译产物，需要定义打的是什么（源码 + node_modules 的 tar？），以及产物落在哪、留几份。
   **这一条同时是 ④ S3 归档的前置**：没有产物就没有可归档的对象。

8. **回滚策略目前只有名字，没有判据。** 需要定的三件事：谁判定要回滚（自动判还是人确认）、回到哪个版本（上一个 commit，还是上一个「部署后验证通过」的 commit，这两者不一定相同）、回滚之后用什么证明已经回到基线。
   W10 的五面 curl + 四项检查提供了证据形态，但「哪一条不绿就回滚」仍是本周要定的判据。

9. **部署动作本身会让 W10 的检查报红。** `systemctl restart nodeapp` 有秒级不可用窗口，check-app 的定时触发可能正好落在里面。
   需拍板：部署期间如何区分「部署造成的红」与「真故障的红」。W10 已有现成形态可沿用（`logger -t DRILL` 的标记思路换成部署标记），但**口径要在第一次自动部署之前定**，否则第一次出现红色结果时无法判断。

### 2.3 一条方法论上的连接（本周真正想拿到的东西）

W9 的方法论收获是「契约先于操作」，W10 是「让状态可以被查询，而不是被回忆」。

W11 对应的命题：**把一段已经能手工做对的操作链交给机器执行，等于把当时藏在脑子里的判断写成显式判据。**
手工部署时「看一眼没问题就重启了」这种隐含判断，在流水线里没有位置：机器要么有一条会失败的检查，要么根本不知道自己做错了。

本周所有动作可以用一句话检验：*这一步如果由机器在我不在场时执行，它凭什么知道自己做对了；做错的时候，它凭什么知道要退回去、退到哪。*

## 3. W11 最小闭环

本周只保留一条主线：

```text
一次 git push
→ 流水线取到这次提交，在受控的构建环境里装依赖并跑测试
→ 测试不过就停在这里，不产生任何服务器改动
→ 通过后按固定步骤把这个提交发布到 W9 的服务器
→ 部署后跑一遍 W10 的验证（五面 curl + 四项检查），结果进构建日志
→ 验证不通过就按预案回滚，并证明回到了发布前的状态
```

**最低交付边界（缺任一条即本周未收口）**：

- 一条能从代码提交走到服务器换版本的流水线。触发形态由 D1 拍板，但「取哪个提交、跑什么、部署什么、验证什么」四项必须是固定且可复现的。
- 一份**发布契约**：部署身份与权限清单、凭据落点、部署单元、本周流水线明确不动的东西、失败判据与止步线。
- **部署后验证复用 W10 的证据形态**：五面 curl + 四项检查手工触发，输出落进构建日志，不另造验证手段。
- **一次真实回滚演练**：故意发一个会失败的提交（测试失败 / 服务起不来两种至少做一种），走完「拦住」或「回滚」的全程，留命令输出作为证据。
- 一份**与 W9 手工部署的对照说明**：同一件事手工要做哪几步、流水线替掉了哪几步、哪几步没有被替掉（仍然需要人判断或执行的步骤）。
- 本周结束时**五面基线全部恢复绿**，与 W9 / W10 的收口证据逐条对齐。

**本周明确不扩展**：

- 不上容器编排（K8s）、不做蓝绿或金丝雀发布（单机单实例没有第二份可切的实例）。
- 不做多机、不做制品仓库（Nexus / Artifactory）、不做配置管理工具（Ansible 等）。
- 不做 Python（W12）、不做前端专项（W13）。
- 不解冻 GitHub Pages；展板发布是否进流水线由 Q7 拍板，默认不进。
- 不改业务逻辑。`server.js` 的类 2 修复属于 W10 移交项，先复现机制再定改动（Q16），不在本周顺手改。
- Java stretch、S3 归档、Docker 统一构建环境三项**都在主线收口之后才开始**，未完成不阻断本周验收。

### 3.1 发布与凭据的安全边界（W11 独有的硬约束）

W10 的硬约束是「故障演练不能把唯一生产机弄坏」；本周的硬约束换了一种形状：**执行者可能不是本人，且可能在本人不看着的时候执行**。

**每一次自动部署的前置四件事（不可省）**：

1. **记录还原点先于发布** —— 部署前先记下当前运行的 commit（`git rev-parse HEAD`）与五面基线结果，这是回滚的目标和对照组。
2. **回滚命令先写好再动手** —— 与 W10 D4 同一条纪律：不是出事之后才想怎么退。
3. **止步条件先写下来** —— 什么现象出现就停止流水线实验、转手工修复（runbook 已经覆盖三类故障）。
4. **部署窗口有标记** —— 本次部署的开始与结束在系统日志里可被一次性过滤出来，用于区分部署造成的红与真故障（Q14）。

**凭据纪律（W10 的日志脱敏纪律在流水线侧的延伸）**：

- 凭据不进仓库、不进构建日志、不进笔记。笔记与提交里一律 redact。
- 密钥由 credentials 机制注入，并且**验证一次 mask 确实生效**（构建日志里查不到），而不是假定它生效。W10 的教训在这里同样适用：没有被验证过的机制不算数。
- 部署身份取最小权限：不用 root，不给全量 sudo，可执行命令写成清单并验证清单外的命令确实被拒。
- 流水线只允许「部署 / 重启 / 验证 / 回滚」这几类动作。**不允许自动改 Nginx 配置、证书、ufw 规则**，这三样是 W9 的收口成果，本周不交给自动化。

**止步线**：一次部署后验证不绿、并且回滚之后仍然不绿，立即停止本周的流水线实验，当天转入手工修复与复盘（按 runbook 走），剩余计划顺延。

## 8. 风险与上限

| 风险 | 判断 | 上限 / 处理 |
|---|---|---|
| **把可写权限交给自动化**（本周新增，W9 以来第一次） | 最高优先级风险；一条过宽的免密 sudo 或一把放错位置的密钥，影响面是整台机器 | 权限清单在 D1 冻结；最小权限 + 清单外命令被拒要有验证证据；流水线不得改 Nginx / 证书 / ufw |
| **自动部署把坏版本推上唯一生产机** | 高；五个公网面同时承载 W9 / W10 的收口证据 | 测试阶段先拦下；部署后验证复用五面 curl + 四项检查；回滚预案在第一次自动部署之前写好并演练 |
| **部署卡在中间态**（依赖装到一半失败，新旧代码混合） | 中高；这种状态比彻底失败更难排查 | Q13 先定原子性策略；部署后验证要能识别中间态，不能只看 HTTP 200 |
| **凭据泄进构建日志或仓库** | 中高；构建日志会打印命令 | 走 credentials 注入并**实测一次 mask 生效**；提交前按 `LEARNING-PROTOCOL.md` §6 第 6 条检查 diff |
| **controller 在开发机导致流水线不可用** | 中；关机 / 休眠即不可用 | Q1 / Q2 显式接受这个代价并写进对照说明的「没被替掉的部分」 |
| **构建缓存与依赖占用磁盘** | 中；check-disk 阈值 4 GB，本周新增一个持续消耗源 | 每次部署后看一眼 check-disk 结果；controller 侧的工作区保留份数要定上限 |
| **在 2 GB 机器上装重组件**（Jenkins agent / JVM / Docker） | 中高；与 W10 监控栈内存教训同形 | 一律先量后装；表内已定 controller 不与部署目标同机，Java stretch 的 JVM 也按此纪律 |
| **8080 明文过渡期仍在线** | 已知短板，W10 移交时记为「未排期」 | Q17 拍板本周做或明确不做；做则走变更单并同步更新五面基线判据 |
| **服务器 Nginx 改动不在 git** | 已知，W9 遗留，备份在机 | 本周若因流水线改动 Nginx（默认不改），同步 `week10-observability/notes/nginx/` 副本 |
