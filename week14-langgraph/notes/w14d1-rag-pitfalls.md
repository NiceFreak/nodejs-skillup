# W14 D1 复盘：W13 RAG 踩坑列表

> 建立：2026-09-14（Asia/Shanghai）。本列表从 W13（9/7–9/11）RAG 学习到 W14 D1 的复盘对话中提炼，记录实际暴露的坑、根因与对应的生产工程正确做法。
> 用途：校准「哪里没做好、正确做法是什么」；下次新建 RAG 工具时作为开工前检查清单。
> 依据：W13 每日笔记、`DEBT.md`、`LEARNING-STATE.md`、day6 桥接记录与本轮对话结论；不含受保护 holdout 内容。

## 摘要

W13 的问题不是「某个组件没做好」，而是「先做了组件，后找它们的意义」。本列表把散落的坑按根因归成五类，每类说明现象、根因、后果、正确做法；另列可迁移的工程纪律。

## 一、锚点缺失：没先回答「什么是 RAG」

- 现象：目标命名为「RAG Foundations」，但「为什么做、为了什么目的」始终未锚定；最小可用行为直到 D5 才想清为「可接入 harness 的 RAG / 独立 RAG agent」。
- 根因：先逐项设计 corpus、chunk、retrieval、eval，后解释这些对象共同服务的系统行为（`AGENTS.md` §1.4 固化的风险）。
- 后果：组件知识聚不成工具，失败无法归因到具体一环。
- 正确做法：阶段 0 先建「目标能力 → 最小可用行为 → 端到端数据流」，再进组件。

## 二、判定口径：阈值无来源 + 分层压成单布尔

- 现象：阈值冻结前未确认（`benchmarkPass=null`）；answered/abstained 用合取判定，出现过「机械+语义合计 ≥9/10」的误读（`DEBT.md` 2026-09-10 条目）。
- 根因：阈值不是「先于数据」确定；分层（结构/身份/语义）被压成一个布尔。
- 后果：无法判断过没过；单布尔让失败无法定位到哪一层。
- 正确做法：在最终评估或发布门禁前冻结阈值，避免在同一正式评测集上反复调参；保留来源、版本和变更理由，支持回放与必要时回滚。结构/身份/语义是本项目的分层诊断设计，不是行业唯一标准；保留分层报告、分项阈值和可解释 verdict，不把诊断结果压成单布尔。

## 三、变量堆叠：没先证明必要性就加变量

- 现象：BM25/dense/RRF 三个后端都跑（retrieval-only 均未过 B4.1：BM25 5/6/7、dense 3/4/5、hybrid 4/5/7，分母 8）；切块当一次性冻结，D5 才发现题目 source span 与 block 边界不相容。
- 根因：未把 overlap、union recall 等分析作为引入 hybrid 的必要性验证；没把「切块质量」当可评估维度。
- 后果：融合是白做的复杂度；边界问题到后期才暴露。
- 正确做法：先最小基线（如 BM25），有明确对比假设和验证动作才加变量；切块是变量，切块质量可评估。是否引入 hybrid，应结合 overlap、增量命中、质量收益和成本验证，不把 overlap 分析写成所有系统的硬性门槛。

## 四、决策锚点缺失：baseline 跑了但没绑定决策

- 现象：full-context baseline 机械 8/10（本人诊断 4/10），但没定义「它要回答什么决策」。
- 根因：没先定义「检索是净收益还是净损失」这个 baseline 的决策用途。
- 后果：8/10 这个数字事后挂不到任何结论上。
- 正确做法：baseline 先绑定决策（例如检索有无价值，或在固定上下文预算下的参照质量），再运行。full-context 只是一个对照基线；只有在模型、prompt、上下文预算和生成设置可比时，检索版本更差才支持“检索或上下文选择造成损失”的假设。

## 五、边界混淆：可运行 ≠ 质量通过，展示 ≠ 质量证据

- 现象：BM25 e2e 10/10 `status=ok` 但人工语义 3/10；dense e2e 9 ok + 1 `schema_error`、机械 7/10、语义 3/10；demo/展板/PPT 三套阅读入口并存。
- 根因：把「结构/解析通过」当成「质量通过」；把「展示材料」当成「质量或掌握通过」。
- 后果：需要反复强调边界，汇报时易误报质量。
- 正确做法：本项目把结构/身份/语义三层分开；运行成功是链路证据不是质量证据；demo/展板/PPT 是阅读入口不是通过证据。其它项目应按任务定义自己的评估维度。

## 六、可迁移的工程纪律（下次任何工具都适用）

1. 等价性验证按替换风险选择维度；生产替换通常至少检查正确性、性能/资源和成本，并明确允许的差异。W13 的 dense 等价性只验证了 top-10 排序一致（最大分数差 7.31e-08），未验证延迟与成本。
2. 在需要归因时优先做受控单变量或可解释消融；失败归因保持「待验证假设」，不写成根因。
3. 通用 holdout/eval 卫生：评测集防污染、在正式评测前冻结授权、不按结果反调 Prompt。仓库的“不读取受保护内容”属于本仓库安全政策，和通用生产 eval hygiene 分开记录。
4. 对检索排序、解析器和 verifier 等可控组件尽量保持确定性；模型输出应记录版本、Prompt、参数和输入，并定义容差或分布级回归。逐字同输出不是所有模型链路可满足的前提（W13 的并列排序规则仍需明确 tie-break）。
