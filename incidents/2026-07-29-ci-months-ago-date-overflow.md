## 1. 一句话摘要

月度销售报表测试用当前时间生成过去月份的订单日期。2026-07-29 运行时，旧版 `monthsAgo(5)` 直接把 7 月 29 日减到 2 月；由于 2026 年不存在 2 月 29 日，JavaScript 自动将日期进位为 3 月 1 日，导致原本应落在 2 月的订单并入 3 月，聚合结果从预期的 6 个月缩成 5 个月，CI 测试失败。修复是在调整月份前先把日期归一到当月 1 日。

2. **观察异常结果** — 实际月份为 3 月到 7 月，没有 2 月；3 月的 `orderCount` 变为 3，`totalSpending` 变为 1998。这说明订单总数没有丢失，而是本应分属 2 月和 3 月的数据被聚合进了同一个月份。

3. **定位** — 测试 fixture 使用下面的旧逻辑生成日期：

   ```js
   const monthsAgo = (n) => {
       const d = new Date();
       d.setMonth(d.getMonth() - n);
       return d;
   };
   ```

   当天是 7 月 29 日，因此 `monthsAgo(5)` 试图得到 2026-02-29。该日期不存在，JavaScript 将结果规范化为 2026-03-01。

4. **修复** — 在 commit `35237e6`（`fix: 2.29 bug`，15:41）中，先执行 `d.setDate(1)`，再调整月份，使目标日期稳定落在目标自然月内。

5. **恢复** — [CI run #30432572202](https://github.com/NiceFreak/nodejs-skillup/actions/runs/30432572202) 的 test 与 frontend job 均成功，test job 于 15:42 完成。

## 5. 根因分析

- **直接原因**：`Date#setMonth()` 保留了当前日期中的“日”。从 7 月 29 日直接回退 5 个月时，目标月份是 2026 年 2 月，但 2 月没有 29 日，JavaScript 自动把溢出的日期推进到 3 月 1 日。
- **测试数据层原因**：测试想表达的是“目标自然月中的一笔订单”，但 fixture 同时继承了测试运行当天的日、时、分、秒。与断言真正相关的只有月份，额外继承的日字段却参与了日期运算并改变分组结果。
- **为什么此前能通过**：这个 helper 的结果依赖运行日期。每月 1–28 日回退到任何月份都不会因为“日”不存在而发生同类进位；2026-07-29 回退到非闰年的 2 月，首次满足了本次溢出条件。
- **为什么结果是 5 个月而不是订单变少**：原本属于 2 月的 `completed` 订单没有消失，而是进入 3 月，与已有的两笔 3 月订单合并。因此返回数组少了一个月份，但总订单数仍然是 7。

## 6. 修复与预防

- [x]（已做）在改变月份前先把日期设为 1 日：

  ```js
  const monthsAgo = (n) => {
      const d = new Date();
      d.setDate(1);
      d.setMonth(d.getMonth() - n);
      return d;
  };
  ```

- **操作顺序是修复的一部分**：必须先 `setDate(1)`，再 `setMonth(...)`。如果先调整月份，日期溢出已经发生，之后再设为 1 日只会得到错误月份的 1 日。
- **fixture 原则**：测试数据只携带当前断言需要的时间维度。这里要验证自然月分组，就先选定每个月都存在的日，再做月份偏移，避免无关的“今天是几号”改变测试语义。

## 7. 经验教训

> 按 `LEARNING-PROTOCOL.md` §9：一次复盘最多沉淀一条可迁移的问题模式。

涉及日历的测试数据不能只看“减了几个月”，还要检查运算保留了哪些更细粒度字段。**当测试契约只关心月份时，先把日期归一到该粒度内永远合法的基准点，再执行月份偏移。** 否则测试会把墙上时钟偷偷变成输入，在月末、闰年或时区边界才暴露不稳定性。
