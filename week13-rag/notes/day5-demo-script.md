## 2. 主讲正文

### 0:00–1:00｜当前做出了什么

**画面**：`rag-roadmap`。沿资料处理、检索、回答与评估的关系指读，再指向后续框架实践；不展开实现细节。

> 我这周用七份固定版本的规则文档，完成了 RAG 输入处理、检索对照和脚本化问答链路。输入是关于规则的问题，
> 输出是带来源的回答，或者证据不足时拒答。
>
> 路线图按能力关系展开：资料处理支撑检索和回答，评估检查各层结果，已有契约再衔接框架实践。
> 接下来主要看三个方面：一个回答怎样追溯到原文，检索怎样改变模型收到的输入，以及这些经验怎样接到框架里。
> 已有真实模型调用记录，也能现场重算本地检索与上下文；页面答案是已有记录回放。
>
> 固定 CLI 链路已经运行，完整质量门禁仍未通过：门禁要求端到端五条条件同时成立、10 题最多错 1 题，
> 检索要求适用题全部命中，目前最高 7/8；这些口径由我冻结，未通过也由我宣布。
> 下面我先展示功能，再用评测解释目前能得出哪些结论。

**过渡**：从路线图进入 `rag-flow`，把视线移到规则文档和可追溯原文片段。首页中文名称介绍对象，下一段再给出对应技术术语。

### 1:00–2:30｜RAG 各层分别负责什么

**画面**：沿 `rag-flow` 读离线准备和提问路径；对照 full-context 分支。

> 语料先经过确定性的 Markdown parser，形成 572 个 source blocks。分块按段落、顶层列表项等规则保留来源；
> 当一段正文需要标题才能解释适用范围时，把必要标题放进模型可见内容。
>
> 每个块都保留 source ID、原始行范围和内容 hash。ID 用来定位来源，hash 检查模型正文有没有变化。
>
> 收到问题后，BM25 给这些块评分，取 top-k，再由 context assembly 按冻结格式组装 Evidence Context。
> 检索结果主要说明选中了哪些块、顺序和分数；Evidence Context 是实际送给模型的正文。它们有明确的转换关系。
>
> 模型收到的是指令、上下文和 query。题目的预期结论与证据要求留在评估端，不发送给模型。
> 返回后，程序先检查 JSON、schema、分支和引用标识；回答是否得到原文支持，再由语义评估判断。
>
> 我也保留了全语料上下文基线：跳过检索，把全部证据送进去。先确认完整输入确实放得下，才能比较检索到底改变了什么。
> 本次输入可完整容纳，所以还不能用“窗口不够”来说明必须做检索。

**可能被问**：chunk 为什么这样划分、ID 与 hash 的区别、为什么保留全语料基线。先记问题，主讲后看附录。

### 2:30–3:30｜为什么这样划分实现职责

**画面**：`rag-implementation`，沿输入、候选、正文、结果之间的交接指读，不逐文件讲源码。

> 这里的代码划分围绕几个需要独立核对的对象。Parser 和 Registry 保留来源位置与正文；检索层只负责候选块的分数和顺序；
> Context assembly 决定哪些文字真正发给模型。这样换检索方式时，可以继续检查相同的来源和输入契约。
>
> 生成层管理请求与返回，评分层再检查运行结果。两者分开，就能看见“调用成功但回答不正确”。
> 当前评分代码还不能独立证明每条引用都进入了输入，更不能替代人工判断原文是否支持结论；展示脚本会补做选定引用的输入成员核对。
>
> 这些边界的价值是帮助定位变化发生在哪一层。接到 LangChain 时，组件接口可以替换，来源身份与判定职责仍需保留。

### 3:30–6:00｜一个回答怎样回到证据

**操作**：进入 `rag-evidence` 的回答示例。先看 query，再看回答，再打开第一条 citation。
点击“重算检索与模型输入”；显示三项 10/10 后继续讲述。终端 `demo-replay.py verify` 是备用路径，不重复执行。

> 这条问题是：技术文案能否用自创概念或助记词，替代官方术语成为后续讨论里的唯一指称？
> 页面给出了 D4 模型返回的回答。接下来我沿着引用看它的依据，而不只看答案听起来是否合理。
>
> 首条 citation 指向冻结 `AGENTS.md` 的第 163 行。点击后可以看到原文，也可以看到模型当时收到的 block。
> block 里有必要标题，原始来源仍然定位到核心规则所在行。这里有三件独立的事：引用 ID 能找到，引用的内容确实进入上下文，
> 以及内容能否支持对应 claim。前两项可以做机械核对，第三项需要理解文字的含义。
>
> 这也解释了为什么要保留 claim 和 citation 的关联：观察者可以逐条追问这句话依据什么，而不是只在回答末尾看到一组文件名。
> BM25 这次端到端运行的人工语义判定已经完成：按 R1 口径通过三条，仍然不通过。所以这里展示的仍然是回答与来源的功能实例，不用它宣布验收通过。
>
> 现在页面重新运行本地 BM25 与上下文组装。十条 dev 问题的检索顺序、上下文 hash 和字符数，都与 D4 记录一致。
> 这证明当前确定性链路能重建那次模型输入里的证据资料；完整请求还包括 Prompt 和 query。生成答案仍然来自 D4 真实调用，这次没有重新生成答案。
>
> 对后续维护而言，这条追溯链很有用：如果答案变化，可以先检查语料、检索集合和输入是否变化，再考虑模型或 Prompt，
> 不需要把所有现象都归到模型不稳定。

**备用**：页面打不开时运行 `case --case w13-dev-direct-answer-02 --section source`。
`verify` 失败时保留错误，只回放原记录；不在现场修改输入或重冻结 SHA。

### 6:00–7:30｜拒答需要结合任务判断

**操作**：同页切换按预期拒答，再切 false abstention。每例只看 query、branch、reason 和预期分支。

> 第二条问题问法语口语稿的词数和格式。当前规则涉及英语口语稿，没有给出法语要求；这次记录返回了拒答和简短理由。
> 这展示了 RAG 的一个边界：任务要求根据给定语料回答时，模型不应直接用常识补上缺失规则。该示例分支符合预期，
> 正式 reason text 的语义判定仍保留待办。
>
> 但拒答本身也不是正确性的保证。另一条问题问在评测契约阶段能否立即把主线切到 MCP，冻结预期是可以依据规则作答，
> BM25 这次却返回了拒答，因此机械分支检查已经失败。
>
> 这两个例子让我把“成功返回一个 JSON”和“完成用户任务”分开，也把正确拒答与错误拒答分开。
> 发现错误拒答之后，还要检查需要的证据有没有召回、有没有进入输入，以及模型怎样使用了它；不能仅凭拒答文本决定根因。

### 7:30–10:00｜检索对照和输入规模说明了什么

**画面**：`rag-eval`。先指 /8 的三种检索结果，再看 /10 的端到端结果与 token 图；分数区现在并列三条端到端的机械通过数（8/10、8/10、7/10）与本人诊断（4/10、3/10、3/10）。

> 我在同一份语料和同一组 dev 问题上比较了 BM25、dense 和 RRF 融合。每种方法取 top-10、20、30，合计九个配置。
> 检索门禁只对八条可回答问题适用，两条无答案问题不要求召回答案证据。
>
> 在这组配置中，BM25 通过数从五条增加到七条，dense 从三条到五条，融合从四条到七条。
> 这说明当前配置下，扩大候选集合找回了部分证据；dense 和融合并没有自动胜过 BM25。
> 这些结果只描述这份语料和配置，不能推广成所有场景下的算法优劣。
>
> 右边是另一个问题：模型输入变小了多少？两次各十题运行中，全语料路径的 provider 输入 token 总量是 447,159，
> BM25 top-10 是 12,723，减少约 97.15%。这是实际记录的输入规模差异。两次缓存命中和输出不同，
> 所以我不会把它直接说成账单或延迟降低了同样比例。
>
> 全语料与 BM25 两条路径的机械通过数都是八条，但失败题不同，不能据此宣布质量相同；dense 端到端另跑过一轮
> 链路验证，机械七条，其中一条是响应结构失败，那一轮只作链路证据、不作质量验收。
> 全语料路径在本人按 R1 复核后，诊断通过数是四条；R1 是在那次运行后明确的，所以要保留诊断口径的时点。
> BM25 与 dense 端到端的人工语义判定已在 D5 完成：按 R1 口径各通过 3/10，两轮仍都不通过，且都只作链路证据。
> 这里最有价值的经验，是把召回、输入规模、格式、引用和回答支持关系分别观察，
> 然后再作取舍。
>
> 当前分数确实未达最初预期：端到端至少要九题通过，检索门禁要求八条适用题全部通过。
> 已观察到漏检、引用问题和错误拒答，但还没有全部隔离根因；可以再具体一点：全语料那轮 6 条不通过里，
> 有 5 条含引用行范围或要求覆盖问题——三条是语义层"没有落在预期规则行范围内的引用"，一条是跨块合并导致不可解析；
> 其中一条还含 claim 内容错误。
> 后续可以分别验证检索排序、上下文呈现和固定输入下的 Prompt 假设，
> 每次保留旧结果并明确要检验哪种原因；目前不能承诺换框架或某个优化就能提分。具体对照留到问答展开。

**错误只作简短经验**：若有余量补一句“JSON 输出约束加入后，那一轮没有再出现格式错误，但 JSON 合法仍不能保证答案正确。”
完整 Prompt 变更史、R1 争议和逐题归因放入追问，不在主讲展开。

### 10:00–13:00｜已有经验如何接到 LangChain 与 LangGraph

**画面**：`rag-framework`。按已用接口、自定义职责、未来候选三列讲解；未实现部分保持虚线或明确标签。

> LangChain 已经进入了当前 BM25 路径。我把 registry 的模型可见正文映射为 `Document.page_content`，
> 把 source ID、行范围、hash 等放进 metadata，再通过 `BM25Retriever.from_documents` 建立检索器。
> 为了满足并列分数时的稳定顺序，我取它底层 vectorizer 的分数后显式排序；当前没有直接调用 `retriever.invoke` 来取结果。
>
> 这次实践让我看到，框架替我提供组件和接口，但来源身份、文本处理、排序规则、实际上下文和通过标准，仍然需要项目自己定义。
> 框架里的临时 ID 不能替代我已经冻结的 citation 身份。
>
> 今天又往前走了一步：dense 的 embedding 与向量存储也接进了 LangChain。我写了一个 Embeddings adapter 承担
> `query: ` / `passage: ` 前缀和向量生成，向量放进 `InMemoryVectorStore`，存储键直接用冻结的 source ID；
> 检索排序仍由项目显式完成，因为框架的并列顺序不满足我们冻结的 registry_index 规则。
> 接线前后我用同一批 dev 查询做了对照：top-10 顺序与集合一致，分数差在 1e-7 量级，冻结的向量缓存和既有证据都没有被改写。
> 生成这一段仍复用此前阶段的模型客户端，没有改用 ChatModel 或 LCEL，所以我不会说整条链都在框架上。
>
> LangGraph 对应的是更进一步的执行需求。当前 RAG 的步骤由程序固定：检索一次、组装一次、生成一次。
> 如果后续任务需要决定是否再检索、何时结束，或者保留执行状态用于恢复，可以把已有检索能力放进节点或工具，
> 由 graph 的 state、节点和边来表达流程。需要持久化时再配置 checkpointer。
>
> 这是一种后续映射，还没有完成 LangGraph 实现。具体继续条件、停止预算和工具权限要先明确，
> 不能因为用了 graph 就认为这些规则自动合理；保存 checkpoint 也不能证明外部动作不会重复发生。
>
> 评估经验可以继续沿用：保留实际执行记录，再分别评价检索、回答支持和工具行为，最后按任务判据决定通过或失败。
> 我希望 W14 的框架实践建立在这组可追溯数据流上，同时与同题固定 RAG 基线比较，让新增流程解决明确的问题。

## 3. 追问与开放讨论：不计入主讲时长

完整准备见 [技术追问附录](./day5-demo-qa.md)。每题先给约 30 秒短答；需要更深时，再定位代码或证据。

优先准备的入口：

1. 分数为什么未达预期？8/10、4/10、/8 分别是什么？哪些优化有验证方法但尚未选择？优先看 Q37–Q43。
2. 为什么语料能放下还研究 RAG？输入规模与质量分别有哪些证据？
3. 你实际使用了哪些 LangChain 能力？为什么生成仍未接入 ChatModel/LCEL？
4. source ID 能解析，为什么仍不能说 citation 正确？
5. dense 为什么没有胜过 BM25？RRF 能解决什么、不能解决什么？
6. JSON 输出约束与 schema 校验各自保证什么？
7. 什么需求值得引入 LangGraph？state/checkpoint 与 RAG 文档库有什么区别？
8. 这套实验如果扩展为持续更新的知识库，还缺哪些能力？
9. dense 端到端跑过吗？接了框架以后九配置对照的结论变了吗？看 Q42–Q43。

被提前打断时可说：“这个问题对应后面的框架/评估页，我先给一句结论……；细节放到主体之后展开。”
需要深入讨论时暂停主讲计时，记录回到哪一页；问答结束后恢复主体，不将讨论时长挤入 15 分钟。

遇到未知问题可说：“我目前的证据能确认……；还没有验证……。下一步会固定其他条件，用……来区分这些可能原因。”
如被问自己做了什么，说明本人拥有需求、冻结语义、review 和判定，AI 承担获准的实现与整理；
用本人实际能解释与诊断的范围回答，不用代码数量或本稿的完整程度替代掌握。
