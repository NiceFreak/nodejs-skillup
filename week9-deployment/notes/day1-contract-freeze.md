### 2.6 部署前置概念（W9 需要但现在还没掌握的基础）

以下是 2026-08-10 对话中暴露出的概念缺口，按原理顺序补齐。**这里只写概念与职责，不写配置。**

#### 2.6.1 云服务器是什么

云服务器 = 一台 24 小时开机的**远程电脑**（本机是 Ubuntu 22.04）。通过 SSH 远程登录它，就像在终端里控制另一台电脑。下面所有组件都装在这台电脑上，而不是装在自己的笔记本上。

#### 2.6.2 服务器上的四个组件各管什么

| 组件 | 类比 | 职责 |
|---|---|---|
| MongoDB | 仓库 | 存数据。数据库软件，装在服务器上 |
| Node.js 应用 | 店铺前台 | 我们的 `week2-express/src/` 代码。处理业务逻辑，需要数据时找 MongoDB |
| Nginx | 门卫 / 接待 | 所有外部请求先到它，它再转发给 Node。**这就是「反向代理」** |
| systemd | 管家 | 保证 Node 和 MongoDB 活着：挂了拉起、开机自启。不让它们变成「手一松就死」的进程 |

#### 2.6.3 反向代理（Nginx 的角色）

**正向代理**是你替自己去访问别人（如公司代理服务器）；**反向代理**是替**服务端**接客——外部只知道 Nginx 的地址，不知道（也不需要知道）后面 Node 的地址和端口。

```text
外部客户端 → Nginx（唯一公开入口）→ Node（内部服务，外部看不到）
```

Nginx 与 Node 通常**同机**，Nginx 用 `127.0.0.1:3000`（loopback）转发。好处：外部只暴露一个入口，Node 可以安全地只监听内部地址（见 2.6.5）。

#### 2.6.4 防火墙是什么、在哪

防火墙**不是独立软件**，是两层：

1. **云控制台安全组**：云厂商层面，按「目标端口 + 源 IP」决定放行，生效在包到达服务器之前。
2. **系统层**：服务器上的 `ufw` / `iptables`（Ubuntu 自带）。

防火墙按**目标端口**过滤，在包**到达进程之前**就做决定。它管的是「从外面进来的请求允不允许进」。

#### 2.6.5 监听地址：0.0.0.0 vs 127.0.0.1

进程的「监听地址」决定它接哪个网卡上的连接：

| 地址 | 含义 | 类比 |
|---|---|---|
| `0.0.0.0` | 所有网卡上的连接都接，包括公网网卡 | 门开在朝外的大街墙上 |
| `127.0.0.1`（loopback） | 只接本机内部的连接，**公网网卡上没有 socket 在等** | 门只开在房间里侧 |

**监听地址和防火墙是两层不同的门**：

- 防火墙：包进大门之前检查，丢包（管「能不能进来」）。
- 监听地址：包到达网卡后，进程接不接收（管「进来了谁接」）。

所以「只靠防火墙」在「规则被误删」时会裸奔（Node 监听 `0.0.0.0`，外部包直接到达）；「代码绑定 127.0.0.1」则在防火墙失效时仍安全（外部网卡上根本没有 socket，包无人接收）。这就是**纵深防御**：两道闸互相兜底。

#### 2.6.6 一次外部请求的完整旅程

```text
浏览器输入 https://域名
  → 公网 IP（43.128.154.242）——服务器在互联网上的门牌号
  → 防火墙保安——目标端口 443？放行！其他一律扔掉
  → Nginx 门卫——接待 HTTPS，转发给内部 Node（127.0.0.1:3000）
  → Node 前台——验证 token、查角色、跑聚合
  → MongoDB 仓库——返回数据（走内部通道 127.0.0.1）
  → 原路返回响应
```

#### 2.6.7 代码如何「上去」

```text
本地代码 → git push → GitHub 仓库 → 服务器 git clone → npm install（装依赖）
→ 创建 .env（密钥）→ systemd 启动 → 进程被管家接管
```

**问题 4（监听边界 / D1）**：`app.listen(PORT)` 现在监听 `0.0.0.0`（第 2.2 节事实）。
「Node 服务只在服务器内部可达」这一条，你打算靠**代码显式绑定 127.0.0.1**、靠**防火墙 / 安全组拦截**，还是两者都要？请说明你选择的方案在「防火墙规则被误删」这个场景下会发生什么。

> 答：**两者都要（纵深防御）**——代码显式绑定 `127.0.0.1` + 防火墙按最小放行兜底。
>
> 推理依据（概念见 2.6.4 / 2.6.5）：
> 1. 监听地址与防火墙是两层不同闸门：防火墙按目标端口在包进入主机前拦截（管「外面能不能进来」）；监听地址决定进程接不接收到达网卡的包（管「进来了谁接」）。`0.0.0.0` = 接所有网卡，`127.0.0.1` = 只接 loopback。
> 2. 正常情况：只靠防火墙就能挡住外部访问 3000——「公网只放行 80/443」会在包到达 Node 之前丢掉。
> 3. **防火墙规则被误删**：方案 A（只靠防火墙、Node 监听 `0.0.0.0`）外部请求能直接到达 Node——裸奔；方案 B（Node 绑定 `127.0.0.1`）外部网卡上没有 socket 在等，包进来无人接收——仍然安全。
> 4. 绑定 `127.0.0.1` 不影响 Nginx 转发：Nginx 与 Node 同机，反代本来就走 loopback（`127.0.0.1:3000`），是同一栋楼里的内线。
>
> 结论：绑定 `127.0.0.1` 作为代码层的「物理防线」，防火墙/安全组作为外部「第一道闸」，互相兜底。误删防火墙仍有绑定兜底；误删绑定（代码回退风险）仍有防火墙兜底。
>
> 落地含义：D2/D3 需将「`app.listen(PORT)` 改为绑定 `127.0.0.1`」列为白名单最小代码改动项（今天第 6 节不改代码，契约先冻结，实施时执行）。

> | 端口 | 监听者 | 来源限制 | 谁需要它 | 不开的后果 |
> |---|---|---|---|---|
> | 443 | Nginx（HTTPS） | 公网 0.0.0.0/0 | 所有外部客户端（浏览器） | 外部完全无法访问服务（唯一 HTTPS 入口） |
> | 80 | Nginx（HTTP） | 公网 0.0.0.0/0 | ① Let's Encrypt 证书签发/续期的 HTTP-01 验证；② http→https 重定向入口 | 证书发不出/续期失败，HTTPS 拿不到或过期 |
> | 22 | sshd | 公网 0.0.0.0/0（本人无固定 IP，限定源 IP 会把自己锁在外面） | 只有本人的管理通道 | 无法远程管理服务器 |
> | ~~27017~~ | ~~MongoDB~~ | — | 只被同机 Node 连（走 127.0.0.1 loopback 内线） | **不在表中**：外部客户端既不需要也到达不了；对公网开放只会暴露数据库端口、放大攻击面 |
>
> 决策推理：
> - **443 必须开**：Nginx 监听、外部唯一入口（第 2.6.6 旅程图）。
> - **80 必须开**：证书验证原理——CA 的 HTTP-01 验证访问 `http://域名/.well-known/...`，从外网来所以 80 必须可达；证书有 90 天有效期，续期要重复走验证，所以 80 要一直开着（而非发完证书就关）。同时 80 可作 http→https 重定向入口。
> - **SSH 开 0.0.0.0/0 的代价**：全网都能尝试连 22。兜底靠**密钥认证**（禁用密码登录）——这是 D2 系统层改动，风险从「弱口令被爆破」降为「密钥不被盗」。
> - **27017 排除的完整理由**：谁需要它 = 只有同机 Node；走什么地址 = `127.0.0.1:27017`（loopback，不经过外部网卡）；外部客户端能否到达 = 到不了（即使端口开着，外部无 socket 可连且有纵深防御）。开放它只有风险没有收益。
>
> 小结：公网只暴露 Nginx（80/443）和 sshd（22），Node 与 MongoDB 都只在内部（127.0.0.1）。

**问题 6（进程守护契约 / D1）**：systemd 单元需要覆盖哪些行为？
至少回答：进程崩溃后是否自动拉起、拉起的退避策略、停止时发什么信号、等多久（对照 `server.js` 的 30 秒关停超时）、开机是否自启、日志去哪里、数据库没起来导致启动失败时你希望它无限重启还是停下来。

> 答：systemd 作为「管家」（2.6.2），覆盖以下契约：
>
> 1. **运行中崩溃 → 自动拉起**：`Restart=on-failure` 语义——进程跑着跑着挂掉（如 OOM）时自动重启，这是「崩溃恢复」验收的核心。
> 2. **退避策略**：重启必须加**退避延迟**。理由：Node 启动依赖数据库先就绪（先 `connectDB()` 成功才 `listen()`，第 2.2 节）。若无退避、MongoDB 未就绪，Node 启动即失败退出，形成高频重启循环——浪费 CPU、刷爆日志，且对数据库恢复没帮助。
> 3. **停止信号**：`SIGTERM`（systemd 默认）——正好是 `server.js` 监听并触发优雅关停的信号（第 2.2 节）。
> 4. **停止超时**：`TimeoutStopSec ≥ 30s`。**硬约束**：若超时比 `server.js` 的 30 秒优雅关停窗口短（如 5 秒），systemd 会在超时后发 `SIGKILL` 强杀，优雅关停被截断、在途请求被掐断。超时必须 ≥30 秒，让进程处理完在途请求再退出。
> 5. **开机自启**：`enabled`——云服务器会因系统更新/迁移/断电重启，不开自启则重启后服务断，没人及时发现。
> 6. **日志去向**：systemd journal，`journalctl` 查看，默认持久化到 `/var/log/journal`。进程 stdout/stderr 被管家集中收集——这正是问题 1c「500 排查顺序第一步看 Node 日志」的证据来源。
> 7. **数据库没起来 → 不无限重启**：达到启动失败次数上限（`StartLimitBurst`）后停止，避免 6a 的空转循环；数据库恢复后由依赖顺序/手动拉起。
>
> 区分两种失败语义：**运行中崩溃**（要自动拉起）≠**启动即失败**（到达上限后停止，不空转）。
>
> 关联：MongoDB 同样是常驻进程，同样需要 systemd 管理（保证运行 + 监听 27017，问题 1 第 5 点）。

**问题 8（复现证据 / D1）**：「按文档能重新走一遍」用什么环境、什么证据来验收？
选项是在现有主机按文档冷路径复核，还是重装 / 新实例重来。请说明你的选择在「文档漏写了一步」这个场景下能不能暴露出来——这是这条验收唯一的价值。

> 答：**主部署完成后，第二遍在现有主机上按文档冷路径从零复核**（不重装），用**清理清单 + 逐项核对**保证起点干净。
>
> 决策依据：
> 1. **只有「从零执行」能暴露文档缺口**——复核动作不是重新读文档检查完整性，而是假装什么都不知道、按文档从头做一遍；漏掉的步骤（如「MongoDB 需要 systemd 管理」）会变成「服务起不来/连不上」这类**可见失败**，而不是被记忆补齐。
> 2. **必须两遍**：第一遍（主部署）时脑子里还有上下文，会无意补全文档漏写；第二遍才假装只信文档。只有一台服务器，而它刚重装是唯一一次「真白纸」——第一遍用掉了这个状态。
> 3. **第二遍起点**：手动停服务、清配置，回到接近白纸。清理方案 = 清理清单 + 逐项核对命令（`systemctl list` / `ls` / `.env` 检查），保证不存在**掩盖式残留**（旧 systemd 单元、旧 `.env`、旧数据、旧 Nginx site 会「跳过文档漏写却依然跑通」，摧毁验收价值）。
>
> **已知残余风险**：清理清单靠人手写，若清单本身漏了某步骤且该步骤没有残留可被核对命令发现，第二遍无法暴露它——这是不重装的代价，记为**已知降级（不影响验收，但文档完整性检验非完美）**。重装能正向保证白纸但使服务器短时不可用，权衡后不选。
>
> **证据形式**：第二遍从零执行全部成功（外部 HTTPS 请求经完整链路返回 200），即证明文档可复现。
>
> 关联：验证接口全程只用 `GET /reports/monthly-sales`（问题 1），第二遍同样用它作为冷路径终点。

### 5.3 一条成功路径 + 两条失败路径

**成功路径**：

```text
1. 浏览器输入 https://43.128.154.242.sslip.io 回车
2. 公网 IP 43.128.154.242 → 防火墙检查目标端口 443 → 放行
3. Nginx（监听 0.0.0.0:443，门卫）接待 HTTPS，检查证书后转发
4. 转发到 127.0.0.1:3000（Node，loopback 内线）
5. Node 进程（systemd 守护）收到请求
6. JWT 验证 → 用 JWT_SECRET 验证 token 有效
7. requireRole 查用户角色（读 MongoDB：127.0.0.1:27017）→ admin 放行
8. 控制器跑聚合（同连接读订单）→ 按月返回销售报表
9. 响应原路返回 → 浏览器显示 200 + JSON
```

明确了两层系统：**信任边界**（外部只能到 443，Node/MongoDB 只在 loopback）+ **状态码梯度**（连不上=连接拒绝/超时；转不进=502；库挂了=500）。

**失败路径 1（启动阶段：MongoDB 挂了 → 502）**：

```text
现象：浏览器访问 → 502 Bad Gateway
根因：MongoDB 没起来 → Node 启动时 connectDB() 失败 → exit(1) → 3000 端口没监听
     （server.js 先连库后 listen，第 2.2 节）→ Nginx 转发失败
先查哪里①：systemctl status <node-service> → 是 failed（Node 根本没起来）
先查哪里②：journalctl 查 Node 日志 → connectDB 报 EHOSTUNREACH/认证失败
关键特征：Node 服务 failed + 3000 端口不存在（ss -tlnp 看不到）
```

**失败路径 2（Node 活着但反代地址写错 → 502）**：

```text
现象：浏览器访问 → 502 Bad Gateway（和路径 1 外部表现相同）
根因：Node 进程活着、3000 在监听，但 Nginx 配置里 proxy_pass 写错地址/端口
      → 转发不到正确的 Node
先查哪里①：systemctl status <node-service> → 是 running（Node 活着，排除路径 1）
先查哪里②：nginx -t 检查配置 + Nginx 错误日志（upstream 错误）
关键特征：Node 服务 running + 3000 存在（ss -tlnp 能看到），但 Nginx 日志报 upstream
```

**对照：运行阶段 MongoDB 挂了 → 500（与 502 的两个场景可区分，见问题 1c）**：

```text
现象：浏览器访问 → 500（请求能进来，查库失败）
根因：Node 进程活着（systemd 里 running）、3000 在监听，但 MongoDB 进程挂了/连接断了
      ——注意与「启动前挂」的区别：启动前挂 = 502，运行中挂 = 500
先查哪里①：journalctl 查 Node 日志 → 定位是聚合代码 bug 还是连接 MongoDB 报错
先查哪里②：systemctl status <mongo-service> / mongosh 连通性
关键判据：状态码梯度——启动前挂(502) ≠ 运行中挂(500)；两者排障入口：前者查 Node 启动，后者查 Node 运行日志 + Mongo 状态
```

**失败路径识别要点**：外部现象相同的 502，用「第一个排查动作」区分——先查 Node 服务状态（failed=路径1 / running=路径2），再按分支看 Node 日志或 Nginx 配置。
