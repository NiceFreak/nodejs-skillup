## 0. 这段 demo 要回答的问题

不是「我把服务部署上线了」。上线是结果，谁都能截一张 200 的图。

真正要回答的是：

> **同一份代码，在我笔记本上和在一台公网服务器上，中间多出来的是什么？每一样为什么必须有？**

这个问法有三个好处：它把 demo 变成对照实验而不是成果展示；它让「本地能跑」这件事从背景板变成参照系；而且多出来的每一样都是可迁移的——换个云厂商、换个语言，这些层还在。

**一句话主张（全场只坚持这一句）**：

> 部署不是把代码搬上去，是**给它加边界**——加完之后，我能说清每一层挡住了谁、没挡住谁。

## 1. 对外呈现边界（开讲前先跟自己确认）

这三条是现场翻车点，先划死：

1. **W9「部署上线」展板不对外演示。** 它把一台在跑的服务器的拓扑、端口和排障判据聚在一页，属复习态资产。对外只用终端 + 浏览器。（自己复盘或内部场合可以开，那时它是最好的提词器。）
2. **不在 8080 上输真实密码。** 那是明文登录表单——而这件事本身就是 Act 3 的第一个素材，别提前用掉，也别为了演示牺牲掉。
3. **密码走密码管理器，不进命令行历史。** 需要登录时用 stdin 形态（`--data @-`），不要把密码写进 `curl` 参数里让它留在 history 和肩后。

## 2. 演示前自检（开讲前 5 分钟，必须自己跑一遍）

**不要跳过。** 这套动线依赖一台真实服务器和三个本地进程，任何一环凉了，现场就只能临场解释——而临场解释恰好是这场 demo 最不需要的东西。

### 2.1 本地三件（按顺序）

```bash
# ① MongoDB（仓库根目录，mongo:7，映射 27017）
docker compose up -d mongo
docker compose ps            # 期望 skillup-mongo 处于 running

# ② 后端（week2-express/src，读 .env，默认 3000）
cd week2-express/src && npm run start
# 另开一个终端验证：
curl -s -o /dev/null -w '%{http_code}\n' http://localhost:3000/    # 期望 200

# ③ 前端（Yarn 3；没有全局 yarn 就用 node .yarn/releases/yarn-3.2.0.cjs dev）
cd week8-fullstack/src/frontend && yarn dev                        # http://localhost:5173
```

### 2.2 云端四条（在本地开发机上跑，不要 SSH 进去自连）

```bash
curl -s -o /dev/null -w '80   /       = %{http_code}\n' http://43.128.154.242/
curl -s -o /dev/null -w '80   /users  = %{http_code}\n' http://43.128.154.242/users
curl -s -o /dev/null -w '8080 /       = %{http_code}\n' http://43.128.154.242:8080/
curl -sS -o /dev/null -w "HTTP_CODE:%{http_code}\nSSL_VERIFY:%{ssl_verify_result}\n" \
  https://43-128-154-242.sslip.io
```

期望：`200` / `404` / `200` / `HTTP_CODE:200` + `SSL_VERIFY:0`。

### 2.3 两个必须提前知道的坑

- **本地的 seed 数据和服务器不是同一份。** 服务器上的锚点是 `258 / 2026-03 / 146988.82`，本地不会是这个数。现场千万别拿服务器的数字去核对本地页面——两边各自出真实数据就够了，这场 demo 要的是「链路通」不是「数一样」。
- **`SSL_VERIFY:0` 在连不上的时候也是 0。** 它是默认空值，只有在连接成功之后才有「证书被信任」的含义。所以自检时要**同时**看 `HTTP_CODE:200`，两个一起才成立。（这条是 D4-HTTPS 执行期实测出来的口径，讲的时候可以顺带说，很加分。）

## 3. 主线动线

### Act 1 · 本地：同一份代码，几乎没有边界（~2 分钟）

**做什么**：浏览器打开 `http://localhost:5173`，登录，进报表页，让月度聚合出数。

**说什么**：

> 这是这个应用在我笔记本上的样子。前端 5173、后端 3000、MongoDB 27017，三个进程，同一台机器。跨域是 Vite 的 dev proxy 抹平的，后端一行 CORS 都没写。

然后把手放在关键的一句上：

> **注意这里没有任何一道门。** 3000 谁都能连，27017 谁都能连，`/users` 这个接口现在是完全敞开的。在本地这不是问题——因为「外面」根本进不来我这台笔记本。

**这一段的作用**：建立参照系。后面每加一层，都是在回答「这台笔记本上不需要、但公网上必须有」的东西。

⏱ 不要超过 2 分钟。这段越干脆，Act 2 的对比越有力。

---

### Act 2 · 云端：同一条链路，多出三层（~4 分钟）

切到第二个终端。**四个 beat，每个约 1 分钟。**

#### Beat 1 · 请求到底走了几跳（~45 秒）

```bash
curl -I http://43.128.154.242/
```

看 `Server: nginx` 和 `X-Powered-By: Express` 两个头一起出现。

> 这两个头同时在，说明请求穿过了 Nginx 又真的到了我的 Express——不是停在 Nginx 的默认欢迎页。链路是：公网 → Nginx:80 → `127.0.0.1:3000` → `127.0.0.1:27017`。
>
> 关键在后面两跳的地址：**3000 和 27017 绑在 127.0.0.1 上，公网根本摸不到。** 它们不是「没在用」——每一个公网请求最后都要经过它们，只是外面进不来。

#### Beat 2 · 同一个 404，两种来源（~1 分钟）

这是全场最值得演的 30 秒。

```bash
curl -s -o /dev/null -w '%{http_code}\n' http://43.128.154.242/users               # 404
curl -s -o /dev/null -w '%{http_code}\n' http://43.128.154.242/nope-12345          # 404
```

> `/users` 是一个**真实存在**的接口，`/nope-12345` 根本不存在——但从公网看，它们的回答一模一样。这是故意的：如果我返回 403，等于告诉扫描器「这个路径是有的，你只是没权限」，那是在给他指路。

接着把两种 404 拆开：

```bash
curl -s http://43.128.154.242/users    | head -c 120   # Nginx 的 HTML 404
curl -s http://43.128.154.242/auth/foo | head -c 120   # Express 的 JSON 404
```

> 但对我自己排障来说，这两个 404 是能区分的：**HTML 的是 Nginx 挡的，请求根本没到应用；JSON 的是 Express 回的，说明已经穿进去了。** 一眼看 body 就知道该往哪一边查——这是白名单顺带给我的免费二分。

#### Beat 3 · 200 只证明活着，0 才证明被信任（~1 分钟）

```bash
curl -sS -o /dev/null -w "HTTP_CODE:%{http_code}\nSSL_VERIFY:%{ssl_verify_result}\n" \
  https://43-128-154-242.sslip.io
```

> `HTTP_CODE:200` 只证明 443 上有个东西在应答。真正证明「证书被系统信任」的是 `SSL_VERIFY:0`。
>
> 这条验收命令我改过两轮才定下来，三个地方都不能松：**必须在本地跑**（在服务器上自连会绕开 DNS、安全组和整条公网链路）；**不能加 `-k`**（跳过校验就把"信任"这半边自废了）；**必须用域名不能用 IP**（证书只签了域名，用 IP 必然 mismatch）。

补一句续期，这是最容易被追问的点：

> 证书 90 天到期。续期不是「我觉得它会自动跑」——`certbot renew --dry-run` 我实跑过一次，模拟续期整个流程走通了。

#### Beat 4 · 三层防线（~1 分钟）

SSH 进服务器，三条只读命令：

```bash
sudo ss -tlnp | grep -E '3000|27017'    # 两个都是 127.0.0.1
sudo ufw status verbose                 # 22 / 80 / 443 / 8080，其余 default deny
systemctl is-active nodeapp mongod nginx
```

> 三层：**进程绑在 127.0.0.1**、**主机上的 ufw**、**云平台控制台的安全组**。三层彼此独立，坏一层还有两层。
>
> 而且它们是能被分别观察到的。放 443 的时候我拿到过一组差分：控制台放行**之前**是 `Operation timed out`，放行**之后**变成 `Connection refused`——超时说明包在云平台就被丢了，拒绝说明包已经进了主机内核、只是还没有进程在监听。**所以「超时」和「拒绝」不是失败程度的差别，是两层给的两种回答。** 超时往外查，拒绝往内查。

---

### Act 3 · 诚实边界：我知道哪里还不行（~1.5 分钟）

**这一段不要跳。** 能主动说出短板，比多演一个 200 有价值得多。

打开 `http://43.128.154.242:8080/`（**只打开，不登录**）：

> 这是管理后台。我现在不在这上面登录——因为它是 8080 明文口。同一个登录表单放在 443 上和放在 8080 上，差的是密码在网络上是不是裸奔。这是个已知短板，下一步就是把 admin 迁到 443。

然后主动交代第二笔：

> 还有一笔我自己欠的账：`/users` 这个接口，**我只在 Nginx 那一层把它挡住了，应用层至今没有鉴权**。反代层挡的是门外汉、扫描器；应用层挡的是「已经登录但不该看这个数据的人」——这两批人不重叠，所以做了一层不等于做完了。今天公网确实摸不到它，因为进应用只有 Nginx 这一条路；但这是缓解，不是修复。

第三笔，一句话带过：

> 再往上还缺 CI/CD 发布回滚、监控告警和备份演练——这些我知道在哪，分别排在后面两周。缺的是成熟度，不是结构。

---

### Act 4 · 收束（~30 秒）

回到开场那个问题，用一句话合上：

> 所以从我笔记本到这台服务器，多出来的是三样东西：**一道把内部服务藏起来的反向代理**、**一层只放行真正被调用的路径的白名单**、**一张能被机器验证的证书**。每一样我都能说出它挡住了谁、没挡住谁——**说得出「没挡住谁」，才算真的懂了它。**

## 5. 追问预案

按被问到的可能性排序。**答不出来的那几条就是 D5 能力检验要补的地方。**

| 追问 | 答法骨架 |
|---|---|
| 为什么上了 443 还留着 80？ | 三个理由：ACME http-01 挑战硬编码走 80，首发和每次续期都靠它；80 是存活锚点，HTTPS 出问题时靠它区分"应用挂了"还是"证书配错了"；将来 301 从 80 发——它是发射台不是拆除目标。 |
| 为什么不用 pm2？ | systemd 是系统自带的、开机自启和日志都在一套里。pm2 我只做了边界对比，没实现第二套——一个进程守护方案讲清楚，比两套都半懂强。 |
| 配置写错了会不会一直重启？ | 不会。`RestartSec=10s` + 60 秒窗口内最多 5 次，超了就 failed 停住。我注入过一次：把 JWT_SECRET 改短，启动校验毫秒级抛错，5 次之后 systemd 拒绝再拉起。但**慢失败不一样**——数据库连不上要等 30 秒超时，一个窗口塞不下 5 次，所以它会一直 restarting，这是设计意图，等依赖恢复自己就起来了。 |
| 502 了先查什么？ | `systemctl status nodeapp`。两条路径的第一个动作是同一个，**把它们分开的是这个动作的结果**：failed → Node 没起来，去看 journal 里 connectDB 报什么；running → Node 活着但请求没送到，去 `nginx -t` 和 error log 的 upstream 行。 |
| 域名打不开呢？ | 先看症状是不是超时，两条相位不共用排查线。超时 → DNS、外部 TCP、本机监听 + ufw、最后差分安全组；不是超时（有回应但不对）→ TLS 握手 + SNI、证书信任、后端反代。**跨相位不串层**，否则会在证书上耗半小时而问题其实在控制台一条规则里。 |
| 反代之后拿得到客户端真实 IP 吗？ | 拿不到，Node 看到的是 127.0.0.1。理论上补 `X-Forwarded-For` 就行，但我读了代码——这个应用一处都没读 `req.ip` / `req.protocol` / `req.hostname`，所以不配。判断规则是"应用读不读"，不是"有没有 HTTPS"。而且真要引入必须**成对**做：只配 Nginx 不设 `trust proxy`，Express 不信任这些头；只设 `trust proxy` 不在 Nginx 覆盖，客户端能自己伪造 XFF。 |
| 数据库为什么不开公网？ | 没有任何理由开。它只被同机的 Node 连，绑 127.0.0.1 + ufw 不放行两道独立防线。开公网等于凭空多一扇门，而门后是全部数据。 |
| 内存够吗？ | 2 GB。实测 mongod 187 MB、nodeapp 84 MB、nginx 8.5 MB，available 还有 1.3 GB 左右。装 Nginx 之前我先量过一次余量才动手——顺带推翻了自己的预测：本来以为 WiredTiger 会按物理内存 50% 吃掉约 450 MB，实测只有 187 MB，它是按需增长不预分配的。**Swap 是 0**，真撞上限没有磁盘兜底，这是现状不是选择。 |
| 你怎么知道重启之后还能起来？ | 跑过。reboot 之后两个服务都是 enabled + active 同秒自起，接口照样出真实聚合数据。不是"配了 enable 所以应该会自起"。 |
