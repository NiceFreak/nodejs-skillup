## 0. 这份方法要解决的问题

W9 的笔记已经很完整（2252 行，含 mermaid 拓扑图、端口表、执行记录、12 条认知修正），但它现在的形态有三个可理解性缺口：

1. **同一件事分散在多处**：端口表在 D1 §5.2、roadmap §1、D4 §5 各出现一次，状态还不同（D1 时 80 未落地、roadmap 里已落地）。读者要自己合并。
2. **时间过程被压成表格**：快失败 vs 慢失败、StartLimitBurst 的 60s 窗口计数、reboot 后自起——这些本质是"随时间推进的状态变化"，用表格只能给结论，给不出"停在第 3 次重启那一刻"的能力。
3. **实测与推演混排**：D1 §5.3 的两条失败路径写得和 D3 B4 的实测记录一样确定，但**502-B（proxy_pass 写错）和 500（运行中挂库）从未真正注入过**。纸面上有"根因/先查哪里"的段落标题保护，做成图之后极易被读成"四条路径都验证过"。

week8 已经把这三类问题的解法建构完成了（统一视觉 token、`framePlayer` 逐帧、证据边界三列 + 口径标注）。本方法的工作不是发明新语法，是**把 W9 的内容接到已经验证过的语法上**，并只在现有语法确实表达不了的地方做最小扩展。

## 1. 判据：什么算"可理解"

沿用 week8 的做法——验收句是"用户不读完整段落也能做出判断"，不是"页面变好看了"。W9 板要让人能当场答出下面六句，答不出就是没做到：

| # | 验收句 | 对应板块 |
|---|---|---|
| 1 | 公网请求最多能摸到哪一层，3000/27017 关掉公网是"没在用"还是"走内线" | ① 信任边界 |
| 2 | 两个 502 外部现象相同，**第一个排查动作**是什么，凭什么判据分叉 | ② 故障分叉 |
| 3 | 配置写错会不会无限重启，DB 挂了会不会被限速停住，为什么这两者结局不同 | ③ systemd |
| 4 | B2 的 200 **没有**证明什么（不证明 Nginx、不证明公网可达） | ④ 端到端验收链 |
| 5 | 反代后哪三类信息失真，为什么本应用决定不补传 | ⑤ 反代决策 |
| 6 | D1 冻结的哪条契约到今天仍然欠着 | ⑥ 契约销账 |

**可理解性是最基本要求**这条，在 W9 有一个 week8 没有的具体含义：W9 笔记的术语密度是全仓最高的（roadmap 自己写了 §8 附录做白话对照）。所以本方法把"术语 ↔ 白话"当作一等公民（见 §2.2），不当作 tooltip 装饰。

## 4. 板块设计（六块）

统一填写模板：认知问题 / 形态 / 展示态 / 复习态 / 数据来源 / **口径边界**。

### ① 信任边界与端口（`topic=boundary`）

- **认知问题**：端口表分散三处且状态不同；"3000 ❌ 不是没在用，是 loopback 内线"这条注解要靠读。
- **形态**：三跳链路图，外套两层面——实线框「公网可达」（22 / 80 已落地，443 灰虚线待做）、点线框「仅本机」（3000 / 27017）；ufw 作为闸门包住公网面。端口表五行与链路联动：点任一行 → 对应跳高亮，并显示「监听地址 / 谁能发起 / 断了什么现象 / 不开的后果」。
- **展示态**：全图 + 五行全展开，443 明确标待做。
- **复习态**：先只给端口号与监听地址，问"哪些公网摸得到、3000 关掉会怎样、27017 为什么不开也能用"，答后揭示。
- **数据**：D1 §5.2 端口表 + §5.1 每跳表；roadmap §1（D4 后状态）；D4 §5 ufw 实际输出。
- **口径边界**：
  - ufw 只是**一层**。腾讯云控制台安全组是另一层（D4 §5「归因预备」已写）。图上必须标"两道闸门"，否则会被读成"ufw 放行 = 公网可达"。
  - 443 从未落地，任何形态都不能画成已完成。

### ② 故障分叉（`topic=failure`）—— 代表页，第一阶段先做这块

- **认知问题**：两个 502 外部现象完全相同，靠"第一个排查动作"区分。这是 W9 迁移价值最高的一条，现在是三段并列的 text 块，靠读者自己对齐。
- **形态**：**同一条链路，四态切换**（正是 week8 认证链 401/403/200 的已验证形态）：

  | 路径 | 停止点 | 外部现象 | 第一个排查动作 | 关键判据 | 证据档 |
  |---|---|---|---|---|---|
  | 正常 | 走完四跳 | 200 + JSON | — | — | measured |
  | 502-A 启动前挂库 | Node 未起，3000 无监听 | 502 | `systemctl status nodeapp` | **failed** + `ss` 看不到 3000 | derived（同形态近似实测，见下） |
  | 502-B 反代地址写错 | Nginx → Node 转发失败 | 502 | 同上 | **running** + `ss` 看得到 3000，Nginx 日志报 upstream | derived |
  | 500 运行中挂库 | 请求进得来，查库失败 | 500 | `journalctl -u nodeapp` | Node running，Mongo 侧异常 | derived |

  **状态码走到停止点之后才揭示**（照搬 week8 第五轮：从一开始就摆着的标签 → 变成推导结论）。
- **展示态**：四条路径可切，默认正常路径。
- **复习态**：先只给"外部现象 = 502"，让人说出下一步查什么、两种判据分别指向哪条；再揭示。
- **口径边界（本板最关键）**：
  - **只有 502-A 有同形态近似实测**——D3 B4 第二轮确实观察到 `failed` 停住且 3000 未监听，但**注入源是 JWT_SECRET 改短，不是 Mongo 挂**。板上必须写清"同形态近似，非本路径直接注入"。
  - **502-B 与 500 从未注入过**，是 D1 §5.3 的设计推演。一律标 `derived`。
  - 四条路径不能一律画成"已验证"。这是本次做成图之后最容易失真的一处。

### ③ systemd 失败模式（`topic=systemd`）—— 逐帧

- **认知问题**：快失败 vs 慢失败是面试常问点，且第一轮注入设计被 `Wants` 语义直接打掉——这两件事都是时间过程。
- **形态**：双路径逐帧时间轴（复用 `framePlayer`），并排同一时间轴 + 实时计数器「60s 窗口内重启次数」。
  - **快失败帧**（按 B4 实测脚本化）：`start` → 启动校验① `JwtSecretConfigurationError` → `exit(1)` → `RestartSec=10` 退避 → 重启计数 1…5（PID 4600 → 4659 → 4733 → 4839，均 status=1/FAILURE）→ ~42s 撞上 `StartLimitBurst` → `failed` 停住 → journal 三条决定性日志（`restart counter is at 5` / `Start request repeated too quickly` / `Failed to start`）。
  - **慢失败帧**：`connectDB` 等 `serverSelectionTimeoutMS=30s` → 60s 窗口内到不了 5 次 → 一直 `restarting`，DB 恢复后自动拉起。
- **附一段「注入设计盲区」三段式**：❌ 原设计（stop mongod → start nodeapp 观察失败）→ ⚡ 被 `Wants` 连带拉起否决（pid 3556 与 3557 相邻同秒）→ ✅ 改快失败注入。这条比结论本身更值得复习：它记录的是**实验设计本身会出错**。
- **展示态**：默认快失败，可切慢失败。
- **复习态**：先问"配置写错会不会无限重启 / DB 挂了会不会被停住"，再放帧。
- **口径边界**：
  - 快失败 = `measured`（PID / 时间 / journal 三类证据齐）。
  - 慢失败 = **`derived`**，从 `serverSelectionTimeoutMS=30s` + 限速窗口推出，**没有真正跑过一次**。标「模型示意」，与 week8 知识点 8（shutdown 顺序取自代码但非计时实测）同一处理。
  - `RestartSec=10s` 是配置值；D2 观察到的 `~11s` 退避是实测值。两者不能混写成一个数。

### ④ 端到端验收链（`topic=chain`）

- **认知问题**：B2 / B3 / D4⑤ 三次端到端读起来像三段重复记录，实际**覆盖段完全不同**。
- **形态**：一条链，三个验收环叠加显示各自起点与覆盖范围：

  ```text
  本地开发机 ──公网──> Nginx:80 ──loopback──> Node:3000 ──loopback──> Mongo:27017
  └────────────────── D4⑤ ─────────────────────────────────────────────┘
                                └──────── B2 / B3（从 127.0.0.1:3000 起）────┘
  ```

  链内逐帧走：`register 201` → 提权 `modified: 1` → `login 200 + accessToken` → `GET /reports/monthly-sales?months=6` → `200 + 真实聚合`。
- **展示态**：三环并列，点任一环显示"覆盖到哪 / 明确不覆盖哪"。
- **复习态**：先给某次验收的起点，问它**没有**证明什么。
- **数据**：B2（2581 单 / ≈155 万 / 8 月 314 单）；B3（`?months=1` → 8 月 314 单 / 191442.37，reboot 后）；D4⑤（2026-03 起 258 单 / 146988.82，经公网）。
- **口径边界**：
  - **三组数字口径不同**（months=6 / months=1 / 不同时间点），**不能并排当趋势读**。板上要显式写这条。
  - **时区观察点必须紧邻本板**：聚合 `$year/$month` 按 UTC、服务器 CST(UTC+8)，凌晨订单跨月归因（7 月 3 单）。不放这里，读者会把"7 月怎么冒出 3 单"当成数据错误。该项仍是 **D5 待决策**，标 `pending`。
  - B2 的 200 **不证明** Nginx 可用、**不证明**公网可达——这正是本板存在的理由，要写在环上而不是脚注。

### ⑤ 反代 header 决策（`topic=proxy`）

- **认知问题**：纯推理内容，笔记里是 §4.2 一段文字；但面试会问，且"XFF 与 trust proxy 必须成对引入"是易错点。
- **形态**：三行 × 三列矩阵——
  | 失真信息 | 理论补传 | 本应用是否消费 | 本次决定 |
  |---|---|---|---|
  | 客户端真实 IP → `127.0.0.1` | `X-Real-IP` / `X-Forwarded-For` | 否（logger 只记 method/url/状态码/耗时） | 不配 |
  | 原始协议 → 恒 `http` | `X-Forwarded-Proto` | 否 | 不配 |
  | 原始 Host → `$proxy_host` | `Host $host` | —（Nginx 默认行为需覆盖） | **配** |

  下挂一条判断规则：应用是否读 `req.ip` / `req.protocol` / `req.hostname` / `req.secure` → 读则 **XFF + `trust proxy` 成对引入**（分开做会拿到不可信的假 IP，且 `proxy_set_header` 的覆盖语义用于防客户端伪造）；不读则只配 `Host $host`。再给落盘的四行 server 块。
- **展示态**：全矩阵 + 结论 + 配置。
- **复习态**：先只给"应用代码读了什么"，让人自己推该配哪些头。
- **口径边界**：`Host $host` 已实测生效（`curl -I` 200 + `Server: nginx/1.18.0` + `X-Powered-By: Express`）；XFF / `trust proxy` 是**未采用方案**，不能画成已配置。

## 7. 口径边界总表（本次最容易做错的地方）

按 week8 第五轮的做法，单独列出来，因为这是唯一会把"可视化"变成"制造假确定性"的风险面。

|---|---|---|---|
