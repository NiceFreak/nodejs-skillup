## 1. Node.js 运行时（事件循环 / 阻塞 / Worker）— W5 ★

### Q1. Node 是单线程吗？异步是怎么实现的？
**A:** 准确说是**执行 JavaScript 的是主线程**，不是"整个进程只有一个线程"。libuv 在底层提供事件循环、I/O 抽象和一个线程池（threadpool，默认 4）。异步 I/O 大多交给操作系统的异步机制或 libuv 线程池，完成后把回调排进队列，**等主线程当前调用栈清空了再执行**。所以"异步"不等于"多开了 JS 线程"。

**★ 加分点**：threadpool 不是所有异步任务的去处。它服务的是 `fs` / `crypto` / `dns` / `zlib` 这类 API；**普通网络 I/O 默认不占 threadpool**（走 epoll/kqueue 这类操作系统机制）。这个区分在排查"为什么并发一高只有某类接口变慢"时是关键。

### Q2. `process.nextTick`、Promise.then、setTimeout、setImmediate 的执行顺序？
**A:** 先分清三个互不隶属的容器：libuv 的**六个事件循环阶段**（timers → pending callbacks → idle/prepare → poll → check → close）、Node 的 **next tick queue**、V8 的 **microtask queue**。nextTick 和 Promise 都**不属于**那六个阶段。每次调度机会，Node 先清 next tick queue，再清 microtask queue，然后才推进事件循环阶段。setTimeout 的回调在 `timers` 阶段，setImmediate 在 `check` 阶段。

**★ 加分点（大多数人不知道）**：nextTick 和 Promise 谁先，**取决于模块系统**。我实测过同一份代码：
```
CommonJS：start → end → nextTick → promise
ESM：     start → end → promise → nextTick
```
因为 ESM 顶层求值本身就在一个 microtask checkpoint 里，求值期间注册的 `Promise.then` 会被并进当前正在清的 microtask 队列，nextTick 反而排在后面。所以"nextTick 永远最优先"是缺上下文限定的简化说法——它不会抢占当前调用栈，也不会中断已经开始的 microtask checkpoint。

### Q3. `setTimeout(fn, 0)` 是 0 毫秒后执行吗？和 setImmediate 谁先？
**A:** 不是。`0`（小于 1ms）会被归一化到约 1ms，它是**最早可调度的阈值**，不是精确执行时刻。顶层同时写 `setTimeout(0)` 和 `setImmediate` 时，**顺序不确定**——我跑 100 次是 94 次 setImmediate 先、6 次 setTimeout 先，受进程启动时机影响。只有在一个 I/O callback **内部**注册两者，才有稳定顺序（setImmediate 先，因为 poll 之后紧接着就是 check 阶段）。

### Q4. 什么代码会阻塞事件循环？（★ 这题里藏着一个我自己纠正过的错，主动讲出来加分）
**A:** 阻塞主线程的是 **CPU 密集的同步 JS**。判断标准不是"这段代码累不累"，而是"它在不在 JS 主线程上跑"。

**我的实测对照**：同一个 `fib(40)`——

| 场景 | 计算耗时 | 并发 `/ping` | heartbeat 最大间隔 |
|---|---:|---:|---:|
| 空闲基线 | - | 约 2–3 ms | 约 102 ms |
| 主线程执行 | 1111 ms | 峰值约 378 ms | 1154 ms |
| Worker 执行 | 1124 ms | 约 2–3 ms | 102 ms |

主线程版把定时器回调和并发 HTTP 请求全拖住了，这就是"阻塞事件循环"的可观察形态。

**★ 加分点（我一开始答错的地方）**：我最早拿 `bcrypt.compare` 当"阻塞主线程"的例子——**这是错的**，我在笔记复查时纠正过。代码里用的是 `await bcrypt.compare(...)`，bcrypt 的**异步** API 通过 N-API 的 `AsyncWorker` 把计算提交到 libuv threadpool，主线程在等待期间继续推进事件循环。只有 `compareSync` 才真的占主线程。所以"CPU 密集"和"阻塞主线程"是两件事，中间隔着"这个库把活派给谁"。

**◇ 边界（受控推断，未直接测量）**：threadpool 默认 4，所以大量并发登录时 bcrypt 会在池里排队——表现是登录变慢，但 `/ping` 仍然快（网络 I/O 不占 threadpool）。我做过 `pbkdf2` 的排队实验，能把**回调完成时间的分布**列为实测事实，但"4+4 分批"这个解释属于受控推断——worker 实际开始时间和纯计算耗时我没有测量到。

### Q5. Worker Threads 解决什么问题？
**A:** 它保护的是**服务的响应性**，不是让计算变快。上面那张表就是证据：放进 Worker 后计算本身是 1124ms（比主线程的 1111ms 还略长），但 heartbeat 和并发 ping 回到了基线附近。

**★ 主动划边界**：本次是**单任务**实验，它没有显示计算加速；Worker 略长的总耗时也只能说可能包含线程创建、通信和调度噪音，我没做归因。它也给不出生产环境的最优 Worker 数量。另外那个 378ms 的 ping 是**计算开始之后**才发出的，所以它是部分等待时长，不是完整阻塞时长——这种口径不说清楚，数字就会被过度解读。

### Q6. Worker 和 libuv threadpool 是一回事吗？
**A:** 不是。Worker Thread 是**你显式创建**的独立 JavaScript 执行线程，有自己的 V8 实例和事件循环，靠消息传递通信。libuv threadpool 是 Node **内部**为部分 `fs` / `crypto` / `dns` / `zlib` API 使用的有限 native worker 资源，你不直接编程它，只能通过 `UV_THREADPOOL_SIZE` 调容量。一个是"我自己开的 JS 线程"，一个是"运行时替我派活的 native 池"。

## 2. Express / 后端架构 — W2 ★（重点强项，尽量往这引）

### Q7. 讲讲你的项目分层。
**A:** 四层，单向依赖：**route**（URL 分发）→ **controller**（翻译官：读 req 参数、调 service、包 res）→ **service**（纯业务）→ **repository**（数据访问）。我有一把很简单的**检验尺子**：全局搜 `req`/`res`，它俩只允许出现在 controller；出现在 service 或 repository 就是越界了。

**★ 加分点**：单向依赖的根据是"**下层不该认识上层**"（依赖方向），跟 Express 是不是洋葱模型没关系——洋葱模型讲的是中间件横向串联，分层单向是纵向架构原则，换任何框架都成立。很多人会把这两个因果搭错。

### Q8. 分层的实际好处是什么？不会太啰嗦吗？
**A:** 最值钱的回报是**换数据库只动 repository**——service 是纯业务、不碰数据库细节，所以底层从写死数组换成 Mongoose 查询时，上面三层几乎不动。第二个是**可测试性**：service 不碰 req/res、不连真库，喂普通参数就能单独测，不用起 HTTP 服务器。至于"service 很薄像没用"——薄不等于该删，它是业务逻辑的预留位，今天没逻辑不代表明天不加"只返回激活用户""按权限过滤"。

### Q9. 400 和 404 有什么区别？在哪一层判断？
**A:** 400 是**请求本身格式错**（比如 `/users/abc`，id 不是数字），404 是**请求没错但资源不存在**（`/users/3`，格式合法查无此人）。落层上：repository 只返回 `undefined`（它不懂 HTTP），由 **controller** 把 falsy 翻译成 404；参数校验也放 controller，在碰 service 之前就拦掉非法输入。判断"有没有"在底层，"返回什么状态码"必须在 controller——还是那把"谁懂 HTTP"的尺子。

### Q10. `/users/:id` 里的 `:id` 是怎么变成参数的？
**A:** `:id` 是占位符，Express 在**路由匹配阶段**把 URL 对应位置的值抓出来、以冒号后的词为键名存进 `req.params`，所以是 `req.params.id` 不是 `req.id`，controller 只是读现成的值。而且值**永远是字符串**——URL 本质是文本，Express 不替你猜类型，这也是为什么底层比较数字 id 时要先 `parseInt`。顺带一组对照：路径参数 `req.params`、查询串 `req.query`、请求体 `req.body`。

### Q11.（★ 强题）讲一条请求从前端到数据库，每层的返回值是什么形状？
**A:** 这题我能一路讲完，而且**每层交付物的形状是不一样的**，这正是分层的价值所在。以 admin 加载月度报表为例：

```text
Dashboard useEffect → fetchMonthlySales() → 从 localStorage 取 token
→ GET /reports/monthly-sales?months=6&status=completed
→ Vite dev proxy → Express /reports router
→ validateToken       // 认证：确认"你是谁"，留下 req.auth = { sub }
→ requireRole('admin')// 授权：用 sub 查库拿当前角色
→ 参数中间件          // 校验并转换 query
→ Controller → Service → Repository
→ Order.aggregate([...]) → MongoDB 执行 pipeline
→ Repository 返回普通对象数组（含 Decimal128）
→ Service 把金额 Decimal128 → Number，返回稀疏月份数组
→ Controller res.json() → 前端 fillMonths() 补齐连续月份 → 渲染
```

**三个容易被追问、而我能答准的点**：
1. **Service 计算业务边界，Repository 只填参数**。"最近 N 个自然月"是业务规则，Service 算出 `[startDate, endDate)` 半开区间；那段 `aggregate([...])` 管道是查询实现，归 Repository。
2. **`await Order.aggregate(...)` 不返回 Mongoose document**。聚合结果不走 document hydration，没有 `.save()` 这类实例方法——所以 Service 对数组做 `.map()` 转 DTO 不会写回数据库。
3. **后端返回的是稀疏月份，前端才补齐**。没有订单的月份后端不造零记录；`fillMonths()` 是**视图需求**（图表要连续时间轴），不是业务数据。数据库执行、DTO 转换、视图补齐是三个不同边界。

**★ 加分点**：这条链不能压缩成"前端请求数据库"。Vite 只做开发代理；认证、授权和成功响应属于不同边界；Repository 调用的是 Mongoose API，**MongoDB 才是聚合的执行者**。

## 3. 认证与鉴权 — W4 ★（强项，密码 / JWT / RBAC / OAuth2 都能纵深）

### Q12. 密码怎么存？为什么用 bcrypt 而不是加密？
**A:** 存的是 `bcrypt.hash(password, 12)` 的哈希，不是明文也不是可逆加密。哈希是单向的——验证时用 `bcrypt.compare(明文, 哈希)`，而**不是**把输入重新哈希再比字符串（因为 bcrypt 每次带随机盐，同一密码两次哈希结果不同，字符串比对必然失败；compare 会从存的哈希里取出盐来算）。数据库里不出现明文，接口返回也剔掉 `passwordHash`。

### Q13. JWT 里放了什么？为什么不放角色？
**A:** 业务自定义 payload 只放 `sub`（用户 id），不放 role/email/name（`iat` / `exp` 是签名库另外生成的）。**不放 role 是刻意的**：role 一旦进了 token，它就是一张**到期前不可变的权限快照**——服务器端把用户提权 / 降权之后，旧 token 直到过期都反映不了最新权限。所以角色判断放到**每次受保护请求实时查库**。

**★ 加分点（把它讲成一个有代价的取舍，而不是"最佳实践"）**：这个选择的成本是**每个受保护请求多一次数据库查询**，换来的是权限变更在下一次请求就立即生效。面试官问"那性能呢"，正面答：这是我知道并接受的成本，如果 QPS 上来，方案是加短 TTL 的角色缓存，而不是把 role 塞回 token。

### Q14. 401 和 403 的区别？
**A:** 401 是**认证**失败——"你是谁"没确认（没带 token、token 无效 / 过期），卡在 `validateToken` 中间件。403 是**授权**失败——身份确认了，但"你能不能"不通过（token 有效但角色不是 admin），卡在 `requireRole`。中间件是分开接的：`validateToken → requireRole("admin") → 参数校验 → controller`，认证在前、授权在后。

**★ 我能拿三条真实路径当证据**（这也是我 demo 的主线）：
```text
无 token      → 停在 validateToken            → 401
member token  → 过认证，停在 requireRole       → 403
admin token   → Controller/Service/Repo/Mongo → 200
```
关键是**同一个资源**的三种结局——这比孤立地背定义有说服力。

**术语**：Authentication = 认证 = 你是谁 = 401；Authorization = 授权 / 鉴权 = 你能不能 = 403。中文"鉴权"口语常把两者混着说，我会刻意区分。

### Q15. 客户端能不能自己把自己提成 admin？
**A:** 不能。注册接口的入参解构只取 `{ name, email, password }`，请求体里就算塞 `role: "admin"` 也会被**静默忽略**——不是靠校验分支挡的，是源头根本没给它进来的机会（**没有校验分支，就没有绕过校验的攻击面**）。注册只创建默认 `member` 且**不签发 token**；改角色只能走运维侧（演示时用 mongosh），不是公开 API。

### Q16. 讲讲 OAuth2 授权码流程。
**A:** 六步：① 开发者先在第三方注册 App 拿 `client_id` / `client_secret`、登记 `redirect_uri`；② 用户点登录，浏览器带 `client_id` / `redirect_uri` / `state` 跳到授权服务器；③ 用户在第三方认证后，浏览器带一次性 `code` 重定向回我们的 callback；④ **后端**用 `code + client_secret` 换 `access token`（这步必须在后端，`client_secret` 绝不能进浏览器）；⑤ 后端用第三方 access token 请求资源服务器拿用户资料；⑥ 根据 `provider + providerUserId` 建 / 绑本地用户，签发**我们自己的 JWT**。

**★ 加分点（凭据边界，这才是面试真正考的）**：`code` 是一次性换票凭据、走浏览器；第三方 `access token` 只在后端、只用于访问第三方资源，**不等于**我们系统的登录凭据；本系统权限仍走自己的 JWT + 查库 role。`state` 在**回调时比对**，防 callback 被串线（CSRF 式注入）；`redirect_uri` 白名单防 code 被送到攻击者地址。

**◇ 边界**：这是**流程级**掌握，我没接真实第三方 provider——这是我当时主动的范围取舍，不是没做完。接真实 provider 的增量主要是注册应用、配回调域名这类工程手感，不是理解上的缺口。

### Q17.（安全）你提到的计时枚举是什么？
**A:** 登录时我对"密码错"和"邮箱不存在"返回**完全一样**的 401 文案（反枚举，避免攻击者靠响应差异探测哪些邮箱注册过）。但**耗时**还有差异：密码错走完一次 `bcrypt.compare`（约 314ms），邮箱不存在提前 return（约 2ms），这个时间差仍可被计时攻击区分。我把它记为**已知安全遗留**，触发条件是上生产 / 公网，优先修复方案是补一次 dummy compare 拉平耗时 + 登录失败限流。我倾向于"讲清楚边界"而不是假装没有。

**注意**（对内提醒，别说错）：这 314ms 是 **threadpool 里的计算时间**，不是主线程被占用的时间——见 Q4。这两处别串台。

## 4. 测试与 CI — W6 ★（最新、最有区分度，主动往这引）

> 这一节是 7/30 新增。它的价值不在"我会写 Jest"，而在**证据意识**：什么结论由测试支持、什么只是巧合、证据能不能脱离你这台机器。多数候选人在这一层是空白的。

### Q18. 你怎么知道你的鉴权是对的？
**A:** 光测成功路径**不够**。这是我这周最想说的一个判断：

> admin 登录后拿到 `200` 这条测试，**排除不了**"授权中间件无条件放行所有登录用户"这个错误实现——因为那种实现下 admin 也是 `200`。

所以必须配一个**反例**：新注册用户（默认 member）真实登录后访问同一个 admin-only 报表，必须是 `403`。**正反两条同时通过，才证明"admin 被放行"且"非 admin 被拒绝"**。我最终的最小证据是这两条链：

```text
已有 admin fixture → POST /auth/login → 真实 accessToken → GET /reports/... → 200
POST /auth/register（默认 member）→ POST /auth/login → 真实 accessToken → GET /reports/... → 403
```

### Q19. 你的测试是怎么分工的？会不会互相重叠？
**A:** 会刻意让它们**各自负责不同的事**，不重复断言：
- **原有的报表集成测试**直接签发 token，绕过登录——它保护的是 **RBAC 分支和聚合数值的正确性**。
- **W6 新增的认证流测试**用真实登录拿 token——它保护的是**真实 token 与资源链的衔接**，**不重新断言聚合数值**。

**★ 这里有个我特意说清楚的点**：W6 是在原有测试**旁边新增**，不是替换掉它。如果直接把旧测试改成走真实登录，就会丢掉"能独立定位聚合逻辑出错"的能力——一条测试失败时你分不清是登录坏了还是聚合坏了。

### Q20. CI 里数据库怎么来的？两个测试套件会不会互相污染？
**A:** CI 的 test job 自己启动一个全新的 `mongo:7` service，通过 `MONGODB_URI` 显式连接（本地缺 URI 时退回 `MongoMemoryServer`；**CI 缺 URI 或库名错误时连接前快速失败**，不静默退回内存库——否则 CI 会"绿得没有意义"）。

隔离是**逻辑库级**的：两个 suite 共享同一个 MongoDB 进程，但分别独占 `skillup_test_a` 和 `skillup_test_b`，所以集合、文档和**唯一索引的命名空间**互不污染。

**★ 加分点**：`--runInBand` 只改变**调度顺序**（串行跑），它**不提供数据隔离**。很多人把串行当成隔离手段——串行只是让污染更难复现，不是让污染消失。

### Q21. 测试全绿是不是就够了？
**A:** 不够。断言全绿只证明**测试观察到的行为**成立，不证明异步资源已经结束。我真踩到过：测试全绿，但数据库里残留空集合和索引——原因是测试结束清库之后，**迟到的模型索引初始化又把集合建了回来**。

修法是在 fixture 之前等待相关 `Model.init()`，teardown 里先 `dropDatabase()` 再断开 Mongoose。之后外部数据库分支**连续 5 轮无残留**。

**◇ 诚实边界**：正常路径已经验证；但异常 teardown 路径仍有缺陷——如果 `dropDatabase()` 或 `disconnect()` 先抛错，后续的资源释放和环境变量恢复会被跳过。这是我记在案的待修项（`try/finally` 层面的小改动），不是我没意识到。

### Q22. 一句话，测试和 CI 各回答什么问题？
**A:**
```text
测试回答：行为可信吗？
CI   回答：这份证据能脱离我这台机器重复吗？
```
本地绿只证明当前这台电脑可以跑通。CI 让同一份证据在一个每次都全新创建、结束即销毁的 runner 上重跑一遍。

### Q23.（会被顺带问）CORS 是怎么回事？能代替认证吗？
**A:** **不能**。CORS 是**浏览器**的跨 Origin 响应访问规则——它约束的是浏览器要不要把响应交付给 JS，挡不住 `curl`、Postman 或任何服务端客户端。认证和授权仍然由 JWT 和服务端规则负责。

**★ 加分点（一个容易搞混的点）**：简单请求（simple request）只是**不触发预检**，不代表跨域就通了——响应里缺少允许源时，请求照样发出去了、服务端照样执行了，只是浏览器不把结果交给 JS。所以"没有 preflight" ≠ "不受 CORS 约束"。

**◇ 我的实际情况**：开发环境用 Vite proxy 保持浏览器同源，所以**这个项目里我没有真正踩过 CORS**。生产拓扑还没验证——如果前后端分属不同 Origin，需要配置并实测 allowlist、允许的方法和 header、preflight 和实际请求；如果走反向代理保持同源，则不需要 CORS。我不把它当成"生产必需项"，它是**条件性**的。

### Q25. 查询慢怎么优化？
**A:** 我不靠直觉，用 `explain` 的硬指标做**前后对照**。我做过一个受控实验：一条关联 `users.name` 字段的 `$lookup`，**唯一变量是这个字段有没有索引**——

| `$lookup` 指标 | 建索引前 | 建 `name_1` 后 |
|---|---:|---:|
| `collectionScans` | 3 | 0 |
| `indexesUsed` | `[]` | `["name_1"]` |
| `totalDocsExamined` | 15 | 0 |
| `executionTimeMillisEstimate` | 12 ms | 3 ms |

核心原则一句话：**你查的字段有没有索引**——它贯穿 `$match` 和 `$lookup`。`_id` 永远自带唯一索引，所以按主键关联天然快。

**★ 主动划边界（这句比数字本身值钱）**：这组数据支持"**当前这条查询**因为新增 foreignField 索引而改变了执行计划、减少了文档扫描量"。它**不能**推出所有 `$lookup` 都需要同一个索引，也**不能**把本机的 12ms→3ms 外推成生产性能。另外这个 `name` 关联和索引只用于实验，做完已经清理；正式报表仍然关联自带索引的 `_id`。

**◇ 提醒**：这题细节多（explain 各字段口径、复合索引 ESR 顺序、覆盖查询），**过了 `db-review-sheet.md` 再主动往深里讲**；没过时答到"用受控前后对照 + `docsExamined` 这类指标说话"这个层面就收住。

### Q26. populate 和 `$lookup`？N+1 是什么？（⚠️ 这题最容易说错，务必按下面的版本答）
**A:** N+1 是指查列表时先查 1 次拿到 N 条，再**对每一条各查 1 次**关联数据，共 **1 + N** 次数据库往返，数据量一大就爆。经典现场是手动循环关联：

```js
const orders = await Order.find();                // 1 次
for (const o of orders) {
  o.user = await User.findById(o.userId);         // 每条 1 次 → N 次
}                                                  // 共 1+N，灾难
```

**三种做法的真实次数**：
| 做法 | 查询次数 | 有没有 N+1 |
|---|---|---|
| 手动循环 `findById` | 1 + N | **有**（灾难） |
| Mongoose `populate` | 1 + 1 | **没有**（用 `$in` 批量） |
| `$lookup` | 1 | 没有（数据库内部关联） |

**⚠️ 千万别说"populate 有 N+1 所以不好"——这是错的。** 现代 Mongoose 的 `populate` 用 `$in` 批量查：`User.find({ _id: { $in: [id1, id2, ...] } })`，代价是**多一次往返**，不是多 N 次查询。

**我实测过**：`mongoose.set('debug', true)` 后跑 populate，14 个订单只发出 **2 条查询**，第二条是 `users.find({ _id: { $in: [4 个 id] } })`——而且 Mongoose 还**去重**了（14 单只属于 4 个 user，`$in` 里只带 4 个 id）。

**怎么选**：层级不同是一切差异的根。`$lookup` 是**数据库层**操作，一次返回，能在管道里接 `$group` / `$project` 做聚合和裁剪；`populate` 是 **Mongoose（应用层 / ODM）**功能，数据库不知道它存在，只"取出引用文档"、不做聚合。只是取出关联文档 → populate（简洁）；关联 + 聚合统计一体 → `$lookup`。

### Q31. 类组件和 hooks 的区别？（考的不是 API，是心智模型）
**A:** 不是语法差异，是两种心智模型：

| 类组件思维 | Hooks 思维 |
|---|---|
| 生命周期："在某个时机做某事" | **同步**："让副作用与某些数据保持同步" |
| 实例（`this`）跨渲染持续存在 | **每次渲染是一次独立的函数调用**，变量被当次闭包捕获 |
| `this.state` 永远指向最新状态 | 每次渲染"看到"的 state 是**那一帧的快照** |
| `setState` 浅合并对象 | `useState` 的 setter **整体替换**（对象要自己展开） |

第二行是理解一切 hooks 陷阱的钥匙：**每次渲染都是一次快照**。

### Q32. 闭包陷阱（stale closure）—— 必考
**A:**
```jsx
const [count, setCount] = useState(0);
useEffect(() => {
  const id = setInterval(() => setCount(count + 1), 1000); // count 永远是 0
  return () => clearInterval(id);
}, []); // 空依赖：闭包捕获了首帧的 count
```
三种解法及取舍：① **函数式更新** `setCount(c => c + 1)`——不依赖外部闭包值，首选；② 把 `count` 加进依赖——正确但定时器每秒重建；③ `useRef` 存最新值——绕过闭包，代价是失去响应式。

### Q33. useEffect 的依赖数组是干嘛的？
**A:** 依赖数组不是"什么时候执行"，是"**效果与谁同步**"。三个容易被追问的点：
- **cleanup 在下一次 effect 之前和卸载时都会执行**，不是只在卸载时；
- **请求竞态**：依赖变化连发两个请求、晚发的先回——cleanup 里置 ignore 标志或用 `AbortController`；
- "useEffect 对应哪些生命周期"是过渡期问法，答完映射要主动补一句：**更准确的模型是"同步外部系统"**。

映射速查：`componentDidMount` ≈ 空依赖 effect；`componentDidUpdate` ≈ 有依赖 effect；`componentWillUnmount` ≈ cleanup；`shouldComponentUpdate` / `PureComponent` ≈ `React.memo`。

### Q34. useMemo / useCallback 什么时候**不**用？（高区分度）
**A:** 背"用于性能优化"只能拿及格分。加分点是反过来讲：
- **默认不用**；先测量再优化，滥用本身有成本（依赖比较 + 内存）；
- 真正需要的三种场景：计算昂贵、引用相等性传给 memo 子组件、**作为其他 hook 的依赖**；
- 趋势：**React 19 的 Compiler 自动做记忆化**，手写 memo 正在退场——知道这个说明你在跟进。

### Q35. Rules of Hooks 的"为什么"？
**A:** 不能在条件 / 循环里调用，因为 React 按**调用顺序**（内部链表 / 索引）把 hook 和它的状态配对；条件调用会让后续所有 hook 错位。能讲出"**顺序即身份**"就超过多数候选人。

### Q36. 状态该放哪？
**A:** 判断顺序不是先选库，而是先问"**谁需要它、刷新后是否应保留、链接是否应可分享**"：
1. 只有单个组件用 → 留在组件内；
2. 兄弟组件共享 → 提升到最近共同父组件；
3. 需要刷新恢复、前进后退、可分享 → **放 URL**（这一条多数人想不到）；
4. 服务端数据的缓存与失效 → 交给服务端状态工具，**不要复制进全局 store**。

2026 的共识是**服务端状态和客户端状态分开管**：服务端数据用 TanStack Query（loading / error / 缓存失效 / 竞态 / 乐观更新开箱即用），客户端全局状态用 Zustand 或 Context——**Context 适合低频全局数据，不是状态管理器的替代品**（高频更新会全树重渲染）。

### Q37. 你什么时候决定做抽象？（开放题，比"会不会写自定义 hook"区分度高）
**A:** 我项目里有个真实例子：一个"时间轴 + 播放控件 + 逐帧解说"的 hook，原先是**某个文件里的私有实现**，直到同样的结构在 **6 处**稳定出现之后才抽成共享 hook——而且**只抽了这三件确定重复的东西，没有抽成通用图形 DSL**。

我的判断是：**先让几个真实调用点证明结构稳定，再抽**。能说出"哪些我特意没抽、为什么"，比背 DRY 有说服力。

## 9. 高频"为什么"速查（被连问时的一句话弹药）

| 问题 | 一句话 |
|---|---|
| 什么阻塞事件循环 | CPU 密集的**同步** JS；`await bcrypt.compare` 走 threadpool，**不**阻塞主线程 |
| Worker 让计算变快了吗 | 没有。它保护主线程响应性；本次单任务实验未显示计算加速 |
| Worker 和 threadpool 一回事吗 | 不是。Worker 是你显式开的 JS 线程；threadpool 是运行时给 fs/crypto/dns/zlib 派活的 native 池 |
| nextTick 一定最先吗 | 不，ESM 顶层里 Promise 会先于 nextTick |
| `setTimeout(0)` 精确吗 | 不，0 是最早可调度阈值（约 1ms），非精确时刻 |
| 为什么 req/res 只在 controller | 它是 HTTP↔业务的翻译层；下层不该懂 HTTP |
| 分层为什么单向 | 下层不该认识上层（依赖方向），与洋葱模型无关 |
| 换数据库要改几层 | 只改 repository，上面三层几乎不动 |
| `Order.aggregate()` 返回 document 吗 | 不，是普通对象数组；不走 hydration，没有 `.save()` |
| 为什么验证密码用 compare 不用重新 hash 比对 | bcrypt 每次带随机盐，同一密码两次 hash 不同；compare 会从存的 hash 取盐来算 |
| 为什么 JWT payload 不放 role | 放了就是到期前不可变的权限快照；代价是每次查库，换权限变更即时生效 |
| 401 vs 403 | 认证失败（你是谁）vs 授权失败（你能不能） |
| 为什么 admin 200 还要 member 403 | 只测成功路径排除不了"无条件放行"的错误实现，反例是必要的 |
| `--runInBand` 提供数据隔离吗 | 不，它只改调度顺序；隔离靠 suite 独占逻辑库 |
| 测试全绿就够了吗 | 不，绿只证明断言成立；曾出现全绿但集合 / 索引残留 |
| 测试和 CI 各回答什么 | 测试：行为可信吗；CI：证据能脱离本机重复吗 |
| CORS 能代替认证吗 | 不能，它只约束浏览器；curl/Postman 不受它管 |
| 简单请求是不是不受 CORS 管 | 不是，只是不预检；缺允许源时浏览器仍不把响应交给 JS |
| 判断查询快慢看什么 | explain 的 `collectionScans` / `indexesUsed` / `totalDocsExamined`，做前后对照 |
| populate 有 N+1 吗 | **没有**，用 `$in` 批量（1+1）；**手动逐条循环**才有（1+N） |
| 怎么证明能力不是 AI 代劳的 | 提交记录不算数；延迟后能独立重建、改需求、预测影响层才算 |
