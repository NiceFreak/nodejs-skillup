## 0.1 从代码读到的日志现状（W10 的起点，非结论）

| 位置 | 现在写了什么 | 形态 |
|---|---|---|
| `week2-express/src/app.js` 首个中间件 | `console.log('logger: ', method, url, statusCode, duration, 'ms')`，挂在 `res.on('finish')` | 单行非结构化文本 |
| `week2-express/src/app.js` error handler | `console.error('Error: ', '<code>: <message>')` | 单行文本，与请求无关联 |
| `week2-express/src/server.js` | 启动 / 关停 / 启动失败的 `console.log` / `console.error` | 生命周期事件，无级别 |
| 落点 | stdout / stderr → systemd → **journald**（`journalctl -u nodeapp`） | 已由 W9 的 systemd 单元决定 |
| Nginx | 四份 server 块各自的 access / error log，Ubuntu 自带 `/etc/logrotate.d/nginx` | **另一条独立日志流** |

**据此可读出四个缺口**（这是 D1 的输入，不是已下的结论）：

1. **不结构化** —— 出事时只能 `grep` 文本，无法按字段过滤（「昨天所有 5xx 的 P95 耗时」答不出来）。
2. **无请求关联** —— Nginx 那条 access log 和 Node 这条 logger 行之间没有任何东西能把它们认成同一次请求；报错时无法从一次公网请求追到应用内的哪一步。
3. **无级别与无脱敏声明** —— 全是 `console.log`，没有 level，也没有任何地方写明「哪些字段永远不许进日志」。当前登录链路会经过 `email` + 密码体，属高危面。
4. **两条流两套口径** —— Nginx 一套格式、Node 一套格式、journald 一套时间戳（W9 已知 UTC/CST 口径问题在这里会再出现一次）。

## 2. 计划分析

### 2.1 合理之处

1. **验收落在「记录」而不是「装了什么」** —— 五段式（现象 → 定位 → 根因 → 修复 → 预防）和「他人照做」是可证伪的终点，装了多少监控组件不是。
2. **和 W9 是同一套环境上的连续动作** —— W9 建立了「链路八层 + 两失败路径 + 改需求预演」的口述能力，W10 正好把它从「能讲」升级为「有工具、有证据、能复现」。
3. **故障清单选得准** —— 端口占用 / 证书过期 / 磁盘满 / OOM / 反代配置错误，五类里有四类**在这台机器上真实可能发生**（证书 11/11 到期、40 GB 盘、2 GB 无 swap、四份 server 块），不是教科书假题。
4. **「进程与内存问题定位」直接吃 W5 的存量** —— 事件循环 / RSS vs heapUsed / libuv threadpool 是 W5 已经实测过的知识，本周是它的运维形态，不是从零学。

### 2.2 与本仓库现状冲突、需要在 D1 拍板的六处

> 下面六条是**问题**，不是答案。逐条的结论由本人在 D1 冻结（§5）。

1. **「集中收集」在单机上没有对应物。**
   Excel 的词面来自多机场景。本项目只有一台机器，「集中」的真实动作是**统一格式 + 统一落点 + 可检索**。
   为了对齐词面去搭 ELK / Loki 会直接撞上 §8 的内存闸门，且解决的是一个本项目不存在的问题。
   **需拍板**：本周把「集中」定义为什么，止步在哪。

2. **「基础监控与告警」的内存预算与 2 GB / swap=0 冲突。**
   Prometheus + node_exporter + Grafana 的常驻内存在这台机器上是可感知的开销，而
   **监控自身把被监控对象压垮**是最典型的反模式。
   **需拍板**：主线用哪一档——(a) 检查脚本 + `systemd timer` + 退出码 + 通知；(b) 只加 node_exporter 留数据不建面板；(c) 完整 Prometheus 栈。
   建议 (a) 为主线、(b)/(c) 降为 stretch 且**先量内存再装**（沿用 W9 对 Java jar 的内存闸门纪律）。

3. **「主动制造故障」与「唯一生产机 + 5 个公网面」冲突。**
   W9 的收口证据（五面全绿、冷启动自起）是本周演练的对照基线，把它演练坏了就没有对照组了。
   **需拍板**：哪些故障可以在生产机上注入、哪些必须隔离、每次注入的止步线是什么（框架见 §3.1）。

4. **pino / winston 是二选一，不实现两套。**
   沿用 W9「systemd 为主实现，pm2 只做边界对比」的纪律：选一个落地，另一个只讲清差异。
   决策输入（L1 讲解，不含实现）：

   | | pino | winston |
   |---|---|---|
   | 默认输出 | JSON，每行一条 | 可配置，默认文本 |
   | 开销取向 | 以低开销为设计目标，格式化尽量移出主线程 | 功能面更宽，transport 生态更大 |
   | 与 systemd/journald 的配合 | stdout JSON 直入 journald，天然对齐「12-factor 日志即事件流」 | 同样可以，但常见用法偏向自己写文件 |
   | 请求中间件 | `pino-http` | 需自行接线或用社区中间件 |
   | 本项目相关性 | 已经是 stdout → journald 的形态，改动面小 | 若选它，要同时决定是否改落点 |

   **需拍板**：选哪个，以及选它的理由是否与「落点决策」自洽。

5. **「日志轮转」的归属可能是个伪需求，要先判断再动手。**
   如果 Node 保持 stdout → journald，**轮转由 journald 负责**（`SystemMaxUse` / `MaxRetentionSec`），
   此时再装一个 logrotate 去转 Node 日志是**给一个不存在的文件配轮转**。
   真正需要 logrotate 的是 **Nginx 的四份文件日志**，而 Ubuntu 已自带 `/etc/logrotate.d/nginx`。
   **需拍板**：Node 日志落点是 journald 还是文件；轮转的责任方随之确定；journald 当前的磁盘占用与上限是多少（这条同时是「磁盘满」演练的前置事实）。

6. **并行线归属与 `LEARNING-STATE.md` 冲突。**~~需拍板~~ → **已拍板（2026-08-17）：以 Excel 为准。**

   `LEARNING-STATE.md`「下一步」第 3 条曾写「W10 起（并行线）：Python/Java 基础学习与 W9 并行推进」，
   而 Excel 把 **Java 挂在 W9（jar）与 W11（Maven job）**、**Python 挂在 W12（第 4 周 8/31–9/4）**。

   **结论**：
   - W10 **不开新语言线**——本周并行线只有**英语**（1–2 篇英文文档 + 一段英文技术总结）与**项目叙述**（5–10 分钟）。
   - W9 未做的 **Java stretch（最小 jar + systemd + Nginx location）并入 W11**，与 Maven 构建 job 一起做；本周不碰。
   - **Python 留在 W12**（8/31–9/4「AI 协作产出 Python 工具」），本周不预习、不铺垫。
   - `LEARNING-STATE.md` 已同步更正，两处描述不再漂移。

   **这条为什么值得单独拍**：它是本周唯一一处「计划自己和自己打架」的地方，而 W9 D5 已经证明
   **「记忆停在旧状态」是最难自查的失效**——两份文件写着不同的下周安排，正是这种失效的种子。
   拍板的实际收益不只是省下学 Java 的时间，是把 W10 的注意力**单点压在观测性上**：本周要练的是定位方法，
   而定位方法只有在自己熟悉的栈上练才有效——在半生不熟的 JVM 上排障，练的是查语法不是查故障。

### 2.3 一条方法论上的连接（本周真正想拿到的东西）

W9 的 D5 已经证明：**「记忆停在旧状态」是最难自查的一种失效**（展板两次说谎、口述 8 处修正里最难的两条都属这类）。
可观测性正是这个问题的工程解——**让系统的当前状态可以被查询，而不是被回忆**。
本周所有动作都可以用一句话检验：*这条日志 / 这个检查，能不能让我在三周后不靠记忆答出当时发生了什么。*

## 3. W10 最小闭环

本周只保留一条主线：

```text
一次真实故障
→ 有统一格式、能定位到单次请求的日志（Nginx 与 Node 两条流可对齐）
→ 有能在故障发生时、最好是发生前就报出来的检查
→ 有一条从现象走到根因的定位路径（而不是靠猜）
→ 有一份别人照做能修的 runbook
```

**最低交付边界（缺任一条即本周未收口）**：

- 一份**日志字段契约**：必有字段、级别口径、**永不入日志的字段**（脱敏清单）、时间戳口径。
- 一次公网请求能被**一个关联 id 从 Nginx 串到 Node**，并在响应头可见。
- 四项检查可运行且**曾被主动弄红过一次**（没红过的告警等于没验证过）：进程存活 / 内存余量 / 磁盘余量 / 证书剩余天数。
- **3–5 类故障**各有一份五段式记录，每份含**至少一条命令输出作为证据**。
- 一份 `runbook`，并通过**延迟自测**：隔至少一天、不看笔记、只按 runbook 走通其中两类故障。
- 演练全部结束后，**五面基线全部恢复绿**（与 W9 收口证据逐条对齐）。

**本周明确不扩展**：

- 不搭 ELK / Loki / OpenTelemetry Collector / APM；不追求「多机集中」。
- 不做完整 Prometheus + Grafana 面板（降 stretch，受内存闸门约束，未做不阻断）。
- 不做分布式追踪、不做日志采样策略、不做 SLO / 错误预算。
- 不做 CI / 自动发布 / 自动回滚 —— 那是 W11。
- **不开新语言线（Java / Python）** —— 2026-08-17 已拍板以 Excel 为准：Java 并入 W11，Python 留在 W12（§2.2 第 6 条）。
- 不下线 8080（见 §9），除非主线已收口且本人另行决定按变更单执行。
- 不修 UTC 时区口径（W9 已明确不修）——但**日志时间戳口径要在 D1 写清楚**，避免排障时把它当成新 bug。

### 3.1 故障演练的安全边界（W10 独有的硬约束）

这台机器是唯一的生产机，承载 5 个公网面，且是 W11 的部署目标。演练必须有边界。

**演练前置四件事（每一类故障都做，不可省）**：

1. **还原点先于注入** —— 要改的配置先备份（W9 的 `shop.bak` 就是先例）；要动的服务先记下当前状态。
2. **先跑一遍五面基线 curl** —— 这是对照组；没有绿色基线就不许注入。
3. **止步条件先写下来** —— 什么现象出现就立即停止演练并回滚。
4. **回滚命令先写好再动手** —— 不是出事之后才想。

**三档分类（初步建议，D1 逐条确认）**：

| 档 | 含义 | 候选故障 | 备注 |
|---|---|---|---|
| A · 生产机可安全注入 | 影响可立即撤销，不写坏持久状态 | 反代配置错误（改一份 server 块 → `nginx -t` → reload）、端口占用（临时进程抢 3000 后重启 nodeapp）、进程被杀（`systemctl stop nodeapp` 观察检查是否报红） | 撤销 = 恢复备份 + reload / start |
| B · 受控注入，需硬止步线 | 会消耗真实资源，超线不可逆 | 磁盘满（在受控目录 `fallocate` 造大文件，**预设保留余量下限与删除命令**）、证书过期（**不动真证书**，用时间口径 / `--dry-run` / 独立测试证书模拟，不触碰 11/11 的现网证书） | 每步都要能一条命令还原 |
| C · 必须隔离环境 | 在 2 GB / swap=0 的生产机上做等于自伤 | OOM（本地 docker 限内存，或服务器上对**临时进程**设 `MemoryMax` 观察 OOM killer，**绝不对 nodeapp 施加**） | 目标是看懂 OOM 的**症状与证据链**，不是真把主服务打死 |

**演练窗口**：集中在 D4，且注入 → 观察 → 修复 → 恢复基线为一个不可拆的单元；一类没恢复不开始下一类。
